# Harucut 설계 문서

결정과 그 근거를 남기는 곳. 코드 주석은 "이 코드가 왜 이런가"를 답하고,
여기 문서는 "왜 이 코드를 택했고 무엇을 안 택했는가"를 답한다.

---

## 한 문단 요약 ① — Lambda 호출을 왜 동기에서 비동기로 바꿨는가

동기 호출은 Lambda 동시성 한도를 만나면 **밀리는 게 아니라 깨진다** — 개선 전 커밋으로
이미지를 만들어 다시 잰 결과(동시 30건, Lambda 동시 실행 한도 10, 스레드 20개)
21건만 성공하고 **9건(30%)이 `429 Rate Exceeded`로 FAILED**가 됐는데,
재실행 스케줄러의 `findStalled`가 PENDING만 보기 때문에 그 9건은 끝까지 회수되지
않고 영구 손실이 됐다(→ [측정 결과](measurement-2026-08-23.md)). `InvocationType.EVENT`로 바꾸면 Lambda가 초과분을 자기 큐에 줄
세우고 재시도하므로 429가 흡수된다 — **처리량이 늘어난 게 아니라 초과분을 버리지 않게 된
것**이다(병목은 우리 스레드가 아니라 Lambda 동시성 한도라, 스레드를 늘려도 처리량은 그대로다).
전환하며 함께 얻은 것이 둘 있는데, 하나는 invoke가 수십 ms에 끝나 요청 스레드에서 바로
불러도 되면서 `composeTaskExecutor`와 `@Async`를 통째로 지운 것이고(합성 1건 8.3초 중
7.9초가 Lambda 안이라 그동안 스레드는 소켓에서 기다리기만 했다), 다른 하나는 결과를 되받는
지점이 생기면서 **실패 관측이 함수 코드 밖으로 나간 것**이다 — 타임아웃·OOM·스로틀처럼
함수가 보고할 수 없는 실패까지 Lambda 서비스가 대신 알려주게 됐다.

> 대가는 "호출의 응답이 더는 결과가 아니다"라는 것이고, 그래서 결과 통지 채널이
> 새로 필요해졌다. 그 선택이 아래 요약이다.

## 한 문단 요약 ② — 합성 결과를 왜 SQS로 받는가

합성 Lambda를 비동기로 바꾸면서 결과를 되받을 길이 새로 필요해졌는데, 함수 코드에서
직접 서버로 HTTP 콜백을 쏘는 방식은 배포로 서버가 30초 내려가는 동안 통지가 그대로
사라졌고(월 33건 ≈ 0.03%), 스로틀처럼 **함수가 실행조차 되지 않는 실패**는 아예 보고할
방법이 없었다. Redis Stream은 지연이 가장 짧지만 서버와 같은 호스트에 있어 서버가 죽으면
통지도 같이 죽고, 별도 HA로 분리하면 월 $25로 후보 중 유일하게 요금이 유의미해지는데
정작 그 스로틀 유실은 여전히 못 막았다. 그래서 **Lambda Destination → SQS를 서버가
롱폴링으로 끌어가는 방식**을 택했는데, 통지를 보내는 주체가 함수가 아니라 Lambda
서비스라서 함수가 죽든 실행이 안 되든 전부 통지가 오고, 큐가 버퍼 역할을 해서 서버가
내려가 있어도 유실이 0이 된다. 결과적으로 배포·스로틀·프로세스 사망 어디서도 Job을
잃지 않으면서, 서버가 자기 속도로 가져가니 과부하 시 배압이 공짜로 생기고, 인바운드를
열지 않아도 되며, 추가 요금은 월 $0.65(Lambda 컴퓨트의 0.25%)에 그쳤다.

> 근거와 반례는 [ADR-0001](adr-0001-compose-result-channel.md),
> 숫자는 [비용 모델](compose-channel-cost-model.md)에 있다.
> **이 결정의 가장 큰 의존점은 "무중단 배포를 아직 안 한다"는 것**이고,
> 그게 바뀌면 HTTP 콜백이 다시 후보가 된다.

## 한 문단 요약 ③ — 큐에서 서버로 왜 롱폴링으로 가져오는가

SQS는 밀어주지 않고 서버가 가져가는 구조라 "어떻게 가져올 것인가"가 남는데, 숏폴링은
큐가 비면 즉시 빈 응답을 주기 때문에 `sleep`으로 주기를 만들어야 하고 **그 주기가 곧
통지 지연이 된다** — 1초로 줄이면 유휴 호출만 월 259만 건이라 무료 티어(100만)를 넘고,
늘리면 사용자가 그만큼 더 기다린다. 게다가 숏폴링은 SQS 서버의 **부분집합만 샘플링**해서
메시지가 있는데도 빈 응답이 올 수 있는데, 우리 큐는 통지가 드문드문 1건씩 오는
저트래픽이라 하필 그게 가장 잘 일어나는 모양이다. 롱폴링은 전 서버를 조회하고 메시지가
도착하면 즉시 반환하므로 **지연과 호출 수를 동시에 개선한다** — 트레이드오프가 아니라
한쪽이 모든 축에서 이기는 선택이었고, 값은 상한인 20초로 잡았다(대기 시간은 "메시지가
없을 때 얼마나 기다렸다 빈손으로 돌아올까"일 뿐이라 통지 지연에는 영향이 없고, 유휴
호출만 인스턴스당 월 26만 → 13만으로 줄어 무료 티어 안에서 3.8대 → 7.7대까지 늘릴 수
있다). 그래서 통지는 도착 즉시 Job에 반영되고, 요금은 사실상 0이며(월 $0.65), 서버가
자기 속도로 끌어가니 과부하 시 배압이 공짜로 생긴다.

> 폴링은 `@Scheduled`가 아니라 **전용 스레드**에서 돈다 — 20초씩 블로킹하는 작업을
> 스케줄링 풀(4개)에 넣으면 새벽 배치와 자리를 다투고, 그 결합이 코드가 아니라
> `application.yaml`의 숫자 하나에 숨는다.
>
> 작업 중 발견: **콘솔에 넣어둔 `ReceiveMessageWaitTimeSeconds=20`은 무시되고 있었다.**
> 요청 파라미터가 큐 속성을 이기는데 코드가 10초를 넘기고 있었다 → [ADR-0003](adr-0003-sqs-consumption.md)

## 이 폴더를 읽기 전에

- **아직 측정하지 않았다.** ADR-0001·0002는 코드와 AWS 문서에서 유도한 논증이고,
  숫자로 못을 박는 건 실험 문서의 몫이다. 실행 전에는 "제안됨"으로 둔다.
- **`decisions.md`는 없어졌다.** 그 내용은 ADR-0001~0004로 쪼개졌고,
  코드 주석의 참조도 전부 ADR 번호로 바꿨다. 이 폴더가 결정의 단일 출처다.

## 미결 (follow-up)

- `compose.stale-after: 10m`은 **Lambda `maximumEventAgeInSeconds`가 300(5분)으로
  설정돼 있다는 전제** 위에 서 있다. 기본값은 21600(6시간)이다. 기본값 그대로면
  10분 뒤 재실행이 아직 살아 있는 이벤트를 다시 던져 같은 합성이 여러 번 돈다.
  지금 그 설정은 `compose-lambda/README.md`의 CLI 한 줄로만 존재한다 —
  IaC로 옮기거나, 최소한 기동 시 실제 값을 읽어 검증해야 한다.
- **합성 파이프라인에 Micrometer 지표가 없다.** "지금 몇 건이 PENDING 인가"를
  볼 방법이 없다. 운영 프로파일에 `/actuator/prometheus` 도 안 열려 있다.
- **`compose_job` 을 지우는 배치가 없다.** 하루 100만 건 기준 1년에 3.65억 행(약 0.9TB)이다.
  파티셔닝은 테이블이 작은 지금이 아니면 못 한다 — [감사 보고서](audit-compose-2026-08-23.md) C-4.
- 그 밖의 미결은 [감사 보고서](audit-compose-2026-08-23.md) 의 실행 순서표를 따른다.
