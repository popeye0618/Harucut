## 0. 한 줄 결론 (현재까지)

**1만 DAU에서 서버는 안 죽는다. 먼저 터지는 건 S3 청구서다.**

RPS를 계산해보니 피크 8, 스파이크 19다. 스프링 부트 한 대가 여유롭게 받는 양이다.
그래서 이 프로젝트에서 "1만 DAU = 서버 증설"은 틀린 답이고, 실제로 급한 건
**저장 비용 → 응답 크기 → 결함 방어** 순이다.

## 3. 개선 ① — 결과물 저장 포맷 PNG → JPEG

### 3.1 문제 인식

합성 결과물을 **무조건 PNG로 저장**한다. 포맷을 고르는 분기가 아예 없다.

| 확인 | 위치 | 내용 |
|---|---|---|
| ✅ | `FourcutRenderer.java:77` | `new RenderResult(encodePng(canvas), encodeThumbnail(canvas))` — 분기 없음 |
| ✅ | `FourcutRenderer.java:231` | `encodePng`는 `ImageIO.write(canvas,"png",out)` 하나뿐 |
| ✅ | `RenderResult.java:6` | 필드 이름이 `fullPng` — **타입에 포맷이 박혀 있다** |
| ✅ | `ComposeHandler.java:62` | `.contentType("image/png")` |
| ✅ | `ComposeService.java:152` | 결과 key가 `job-{id}.png` |

**알파가 필요 없다는 건 코드가 자백한다.** `FourcutRenderer` 주석에
*"합성 결과는 배경이 항상 칠해져 있어 잃는 픽셀이 없다"*고 적혀 있고,
**썸네일은 이미 JPEG q0.8로 저장 중**이다 (`:58`, `:245`).
원본만 PNG인 이유가 코드에도 문서에도 없다 — `docs/adr-*.md` 전수 검색 결과 PNG 근거 **0건**. 📄

### 3.2 왜 급한가 — 돈

📄 감사 문서 실측: 같은 캔버스가 **PNG 14.4MB / JPEG q0.90 2.72MB** (5.3배).
이 값을 §1 트래픽 모델에 곱하면:

| | PNG | JPEG q0.90 |
|---|---|---|
| 일 저장 | 211GB | 39.8GB |
| 월 신규 | 6,412GB | 1,211GB |
| 12개월 누적 | **77TB** | 14.5TB |
| **12개월차 저장료** ($0.025/GB·서울) | **$1,924/월** | $363/월 |
| egress (1회 다운로드 가정, $0.09/GB) | $577/월 | $109/월 |

> 🔢 **12개월차 월 절감 약 $2,028 (≈294만원).**
> 단, 이건 감사 문서의 크기 값을 그대로 쓴 계산이다. 자체 실측으로 교체한다 (☐ 1-1).

부수 효과도 크다. 📄 PNG 인코딩이 렌더 시간의 **74%**다. JPEG로 바꾸면
건당 8.3초가 줄고, **Lambda 동시 실행 필요량(§2 후보 3번)도 같이 내려간다.**
사용자 체감으로도 14.4MB를 LTE 10Mbps로 받으면 11.5초, JPEG면 2.2초다. 📄

### 3.3 발견한 함정 — "한 줄이면 된다"는 틀렸다

처음엔 `encodePng` → `encodeJpeg` 치환 한 줄이라고 봤다. **아니었다.**

**함정 (1) 색 공간.** ✅ `FourcutRenderer.java:66`이 캔버스를 `TYPE_INT_ARGB`
(알파 포함 4채널)로 만든다. JPEG는 알파를 지원하지 않아서, ARGB를 Java 기본
JPEG writer에 그대로 넣으면 색이 깨지거나 예외가 난다.

기존 `encodeJpeg`(`:280`)가 멀쩡히 도는 이유는 **썸네일 경로만 우연히 RGB로 변환되기 때문**이다:
`encodeThumbnail`(`:245`) → `scaleToLongEdge` → `drawScaled`(`:268`)가
`TYPE_INT_RGB`로 **새 이미지를 그린다.** 원본은 그 경로가 없다.
→ **ARGB→RGB 평탄화가 먼저 필요하다.**

**함정 (2) 품질이 상수에 묶여 있다.** ✅ `encodeJpeg`(`:280`)가
`THUMBNAIL_JPEG_QUALITY = 0.8f`(`:58`)를 직접 읽는다. 원본에 다른 품질을 쓰려면
품질을 인자로 빼야 한다. 지금 구조로는 썸네일 품질을 바꾸면 원본도 같이 바뀐다.

**함정 (3) 배포 순서.** 서버가 `.jpg` key를 만드는데 Lambda가 아직 옛 버전이면
**`.jpg` 파일에 PNG 바이트가 들어간다.** 반대 순서면 `.png`에 JPEG가 들어간다.
어느 쪽이든 확장자·`contentType`과 실제 내용이 어긋나는 창이 생긴다.
→ 이 프로젝트는 **썸네일 도입 때 같은 문제를 겪고 이미 풀어봤다**:
`ComposeLambdaPayload.thumbnailKey`를 null 허용으로 두고 Lambda가
*"필드가 없으면 옛 동작"*으로 떨어지게 했다 (`ComposeHandler.java:66-71` 주석).
**같은 패턴을 재사용할 수 있다** — 포맷을 payload에 실어 서버가 지시한다.

**함정 (4) 테스트 18곳이 픽셀을 본다.** ✅ `FourcutRendererTest`가
`decode(result.fullPng())`(`:367`)로 결과를 디코드해 픽셀을 단언하는 테스트가 18개다.
JPEG는 손실 압축이라 픽셀 값이 정확히 일치하지 않는다.
**다행히 `assertCloseTo(actual, expected, tolerance)`(`:374`)가 이미 있다** —
허용 오차를 받는 형태로 설계돼 있어서 구조를 갈아엎을 필요는 없다.
다만 **tolerance를 몇으로 둬야 하는지는 측정해야 한다** (☐ 1-3).

### 3.4 측정 ✅ (1-3·1-5 제외)

도구: **JUnit 마이크로벤치** (`compose-core/src/test/.../EncodingBenchmark.java`).
렌더러가 순수 자바라 스프링·DB·AWS 없이 잰다. 실행은 §8 참고.

| # | 측정할 것 | 결과 |
|---|---|---|
| ✅ 1-1 | 포맷별 크기·인코딩 시간 | 아래 표 |
| ✅ 1-2 | ARGB→RGB 평탄화 비용 | **CLASSIC 28ms / GRID 55ms** — 절감분의 2%. **이득에서 뺄 필요 없다** |
| ☐ 1-3 | 픽셀 tolerance | 아직. `JpegToleranceProbe` 미작성 |
| ✅ 1-4 | 렌더 전체 중 인코딩 비중 | **40~84%** — 아래 표 |
| ✅ 1-5 | 눈으로 확인 | **q0.90이 q0.85보다 확실히 낫고, q0.95는 q0.90과 구분이 안 된다** |

**환경**: Windows 11 · JDK 21 · 힙 2g · 워밍업 1회 / 측정 3회 중앙값
**입력**: 생성 이미지 3종(고정 시드, 1000×1500) + 실사진 4장(아이폰, 5712×4284 ×3 + 4032×3024)

#### 1-1 포맷별 크기 — 실사진 기준

| 프레임 | PNG | q0.85 | q0.90 | q0.95 |
|---|---|---|---|---|
| CLASSIC 2000×6000 | 14.44MB | 1.29MB | **1.61MB** | 2.33MB |
| GRID 4000×6000 | 25.48MB | 1.99MB | **2.49MB** | 3.64MB |

**PNG 대비 9~10배.** 인코딩 시간은 GRID 기준 3,483ms → 825ms(**4.2배**).

q 구간별 증가율은 생성 이미지·실사진 양쪽에서 동일하게 재현됐다:

| 구간 | 증가 |
|---|---|
| q0.85 → q0.90 | **+25%** (생성 이미지 +28~35%) |
| q0.90 → q0.95 | **+45%** (생성 이미지 +46~64%) |

→ **가성비의 무릎이 0.90과 0.95 사이다. q0.95 탈락.**
인코딩 시간은 q에 거의 반응하지 않는다(+21%) — **q 선택의 변수는 시간이 아니라 크기다.**

> **생성 이미지 편차 주의** 🔢 — 같은 코드가 입력에 따라 이렇게 갈렸다(GRID):
> PNG 24.71~46.94MB(1.9배), **q0.90 1.20~5.83MB(4.9배)**.
> **JPEG가 내용에 훨씬 민감하다.** §3.2에 단일 평균값을 쓰면 안 되는 이유다.
> 실사진은 `매끈`과 `경계` 사이에 있었다 — 감사 픽스처보다 내 `노이즈강`(σ=40)이 과했다.

#### 1-4 렌더 단계별 비중 — 인용값 74%는 조건부였다

| GRID | 그리기 | PNG 인코딩 | render 전체 | PNG 비중 |
|---|---|---|---|---|
| 생성 이미지(150만 화소 입력) | 1,019ms | 5,803ms | 6,941ms | **84%** |
| **실사진(2,450만 화소 입력)** | **2,980ms** | 3,461ms | 6,572ms | **53%** |

**⚠️ 여기서 예상 못 한 게 나왔다.** 입력 해상도가 커지자 **그리기가 3배로 뛰었다.**
슬롯이 1700×2400인데 5712×4284 원본을 그대로 받아 줄이고 있다 —
**렌더 시간의 절반 가까이가 "필요 없이 큰 원본을 축소하는 데" 쓰인다.**

→ 그래서 개선 ①의 렌더 단축 효과는 **67%가 아니라 39%**다(GRID 6,572ms → 약 3,991ms).
→ 그리고 **새 후보가 생겼다: 업로드 해상도 축소** (§2 후보 9번).

> 캔버스 크기 참고 ✅ (`FrameType.java`): CLASSIC 2000×6000, WIDE 6000×4000,
> GRID 4000×6000, POLAROID 4000×6000. 감사가 잰 건 GRID(4000×6000)다.
> **24M 픽셀 × 4바이트 = 캔버스 하나가 메모리에서 96MB**라는 것도 같이 기록해둘 것.

### 3.5 결정

- [x] **포맷: JPEG.** WebP는 미룬다 — 이득의 94%가 PNG 탈출에 있고(PNG→JPEG $3,992/월,
      JPEG→WebP $117/월 🔢), JDK에 인코더가 없어 네이티브 바이너리가 배포물에 들어온다.
      `compose-core`가 순수 자바인 성질(이 벤치가 인프라 없이 도는 근거)이 깨지고,
      아직 안 한 arm64 전환과 순서가 꼬인다. → ADR로 별도 기록
- [x] **q0.95 탈락** — 크기 +45%인데 인코딩 시간은 +21%뿐. 무릎 바깥이다
- [x] **품질값 q0.90** (q0.85 아님) — 근거는 **돈이 아니라 돈의 크기다**:

      | | 파일 | 저장+전송(12개월차) |
      |---|---|---|
      | PNG | 25.48MB | 월 $4,425 |
      | q0.85 | 1.99MB | 월 $346 |
      | **q0.90** | **2.49MB** | **월 $433** |

      q0.85로 더 아끼는 건 **월 $87 — 전체 절감액의 2%**다.
      그 2%를 아끼려고 화질 여유를 깎을 이유가 없다.
      ✅ **육안 확인(1-5)도 같은 답을 냈다** — q0.90이 q0.85보다 확실히 낫고,
      q0.95는 q0.90과 구분이 안 된다. **돈과 눈이 같은 지점을 가리켰다**
- [x] **기존 `.png`는 그대로 둔다** — 읽기 경로에 확장자 하드코딩이 없어(Swagger 예시뿐)
      `.png`와 `.jpg`가 섞여도 동작한다. **변환 배치는 필수가 아니라 선택**
- [x] **포맷을 payload에 싣는다** (함정 3) — 서버가 지시하고 Lambda는 따른다.
      배포 순서 문제가 사라지고, 나중에 WebP로 갈 때 Lambda만 교체하면 된다
- [ ] `RenderResult.fullPng` 이름 변경 범위 — 구현 단계에서

> **되돌릴 수 없는 결정이라 측정을 먼저 했다.** 합성 성공 시 원본 4장을 지우므로
> (`ComposeService.java:113`) 재합성이 불가능하다. 낮은 q로 굴린 기간의 결과물은
> **영구히 그 화질**이다. 그래서 순서가 "전환 → 측정"이 아니라 "측정 → 전환"이었다.

### 3.6 구현 ✅ — 배선과 flip을 커밋으로 갈랐다

두 커밋이다. **커밋 경계가 곧 배포 경계다.**

1. **배선** — 포맷을 payload 계약으로 (`ComposeLambdaPayload.outputFormat`, null이면 PNG 폴백).
   키 확장자·바이트·contentType이 전부 `ComposeService.RESULT_FORMAT` 한 상수에서 파생된다.
   이 커밋까지는 결과물이 안 바뀐다 (RESULT_FORMAT = PNG)
2. **flip** — `RESULT_FORMAT = JPEG` 한 줄 + Swagger 예시 정리.
   **그 사이에 Lambda를 먼저 배포하고 스모크로 확인했다** — 새 Lambda + 옛 payload로
   합성 1건, 결과 매직넘버 `89 50 4E 47`(PNG) 확인. 폴백이 실전에서 동작한다

썸네일 도입 때(`thumbnailKey` null 허용)와 같은 패턴이다. 이 저장소에서 두 번째 사용.

### 3.7 검증 ☐ — flip 배포 후

- ☐ 운영에서 합성 1건 → `job-{id}.jpg` 매직넘버 `FF D8 FF`(JPEG) 확인
- ☐ 옛 `.png` 미디어와 새 `.jpg` 미디어가 목록·다운로드에서 함께 동작하는지
- ☐ 렌더 시간 지표(Micrometer)에서 인코딩 단축이 보이는지 — §3.4의 39% 예측과 대조
- ☐ S3 버킷 크기 증가 속도 변화 (며칠 뒤)

## 4. 개선 ② — 페이징 `size`에 상한이 없다

### 4.1 문제 인식

✅ `PageRequests.java`:

```java
if (page < 0) { ... }   // :14  하한 있음
if (size < 1) { ... }   // :17  하한 있음
return PageRequest.of(page, size);   // :21  상한 없음
```

`?size=1000000`을 그대로 받아 DB에 `LIMIT 1000000`으로 내려보낸다.

**호출부 5곳** ✅ — 하나만의 문제가 아니라 **공용 입구의 문제**다:

| 호출부 | 대상 테이블 | 1년 뒤 행 수 🔢 |
|---|---|---|
| `UserMediaService.java:39` | `user_media` | **547만** |
| `NoticeService.java:25` | `notice` | 적음 |
| `NoticeAdminService.java:55` | `notice` | 적음 |
| `PaymentHistoryService.java:28` | `payment_order` | 중간 |
| `TermsAdminService.java:73` | `terms_agreement_history` | 중간 |

### 4.2 왜 급한가 — DAU와 무관하다

이건 트래픽이 늘어서 생기는 문제가 아니라 **처음부터 방어가 없는 자리**다.
1만 DAU가 하는 일은 **피해 규모를 키우는 것**뿐이다 — `user_media`가
547만 행이 되면 같은 요청 하나의 무게가 달라진다.

§2에서 이걸 🔴로 둔 이유도 "1만 DAU라서"가 아니라 **"지금 이미 결함이라서"**다.

### 4.3 측정 계획 ☐

측정보다 **재현**이 맞는 항목이다. 성능 수치를 뽑는 게 아니라
"막지 않으면 무슨 일이 나는가"를 보여주면 된다.

| # | 확인할 것 | 방법 | 나와야 하는 값 |
|---|---|---|---|
| ☐ 2-1 | 큰 `size`가 실제로 어디까지 가는가 | `size=1000000` 요청 후 실행된 SQL 확인 | `LIMIT`에 그 값이 그대로 실리는지 |
| ☐ 2-2 | 힙·응답 시간 영향 | 행을 채운 뒤 같은 요청 | 메모리·ms |
| ☐ 2-3 | 상한값을 얼마로 둘 것인가 | 프론트가 실제로 쓰는 페이지 크기 확인 | 정수값 |

## 5. 개선 ③ — 프레임 목록이 안 쓰는 데이터를 다 실어 보낸다

### 5.1 문제 인식

✅ `FrameService.getMyFrames`(`:41-56`)가 매 요청 이렇게 한다:

```java
Stream.concat(myFrames, frameRepository.findAllWithComponentsBySystem().stream())   // :54
      .map(frameComponentAssembler::toFrameResponse)                                 // :55
```

그리고 `toFrameResponse`(`FrameComponentAssembler.java:156`)는
**컴포넌트마다 presigned URL을 발급한다** (`:160` → `FrameAssetManager:49` → `:64`).

**문제가 세 겹으로 겹쳐 있다:**

| # | 문제 | 확인 |
|---|---|---|
| (1) | 시스템 프레임을 **모든 사용자에게 매 요청 통째로** 조회. 결과가 전원 동일한데 캐시가 없다 | ✅ `FrameRepository:19` / 저장소 전체에 `@Cacheable` **0건** |
| (2) | `where is_system = true`에 **인덱스가 없다** | ✅ `Frame.java:19` `@Table(name = "frame")` — 인덱스 선언 없음. `is_system`은 `boolean`이라 FK 자동 인덱스도 안 붙는다 |
| (3) | 목록이 **화면에서 안 쓰는 컴포넌트와 그 URL을 전부 실어 보낸다** | ✅ 아래 |

### 5.2 (3)이 핵심 — 프론트는 목록에서 미리보기만 쓴다

**프론트 동작 (사용자 확인):** 목록 화면은 **미리보기 이미지만** 보여준다.
컴포넌트를 실제로 그리는 건 **항목을 눌러 들어간 상세 페이지**다.

그런데 목록 응답에는 프레임마다 `components[]`가 통째로 들어 있고,
그 안의 `PHOTO`마다 presigned URL이 발급돼 있다.
→ **발급 비용과 응답 크기를 지불하는데 화면은 그걸 안 쓴다.**

🔢 계산: 시스템 프레임 50개 × 컴포넌트 8개 = 400 + 프리뷰 50 = **약 450회 presign**,
URL 1개를 600바이트로 잡으면 **응답 약 270KB**.

> ☐ **이 숫자는 전부 가정이다.** 시스템 프레임이 몇 개인지 모른다. 측정으로 교체한다.

### 5.3 설계 제약 — 캐시에 URL을 담으면 안 된다

✅ presigned URL은 **24시간 만료**다 (`S3FileStorageService.java:28` `EXPIRY`).
(1)을 캐시로 풀 때 **URL이 들어간 응답을 통째로 캐시하면 죽은 URL을 서빙하게 된다.**

→ **key만 캐시하고 서명은 요청 시점에** 하거나, 캐시 TTL을 만료보다 충분히 짧게.
이건 캐시를 붙이기 전에 정해야 하는 제약이라 여기 먼저 적어둔다.

### 5.4 측정 계획 ☐

도구: **통합 테스트 + 쿼리 카운트**. 이 저장소엔 이미 쓸 수 있는 패턴이 있다 —
`FrameListQueryCountTest`가 Hibernate 통계로 `SELECT` 횟수를 세고 있다. ✅

| # | 측정할 것 | 방법 | 나와야 하는 값 |
|---|---|---|---|
| ☐ 3-1 | 시스템 프레임 실제 개수·컴포넌트 수 | DB 조회 (또는 운영 기준값 결정) | 개수 |
| ☐ 3-2 | 목록 응답 실제 바이트 | `MockMvc` 응답 길이 측정 | KB |
| ☐ 3-3 | 요청당 presign 호출 횟수 | `FileStorageService` 스파이로 카운트 | 횟수 |
| ☐ 3-4 | presign 1회 CPU 시간 | 마이크로벤치 | μs |
| ☐ 3-5 | 요청당 쿼리 수 | `FrameListQueryCountTest` 패턴 재사용 | 개수 (예상: 5) |
| ☐ 3-6 | `is_system` 인덱스 유무 효과 | 행을 채우고 `EXPLAIN` | 스캔 행 수 |

### 5.5 결정 ⏸ — 계약 변경 범위 (가장 중요한 결정)

**아직 정하지 않았다.** 측정값을 보고 정한다.

| 안 | 내용 | 응답 크기 🔢 | 프론트 영향 |
|---|---|---|---|
| A | 캐시 + 인덱스만 | 270KB → 270KB | 없음 |
| B | 목록에선 `key`만, URL은 상세에서 | 270KB → 약 40KB | 있음 |

## 7. 조사하다 발견한 잘된 것

문서에 남길 가치가 있어서 적어둔다.

**인덱스 전략이 일관돼 있다.** 처음엔 `frame`·`user_media`에 `user_id` 인덱스가
없다고 봤는데 아니었다. 패턴이 이랬다:

| 연관 방식 | 인덱스 출처 | 해당 엔티티 |
|---|---|---|
| `@ManyToOne @JoinColumn` | **MySQL이 FK에 자동 생성** | Frame, UserMedia, ComposeJob, FrameComponent |
| 그냥 `Long userId` (FK 없음) | **`@Index` 직접 선언** | UserCoupon, BillingKey, PaymentOrder, Payment, TermsAgreementHistory |

명시 인덱스가 정확히 **"FK가 없어서 자동 인덱스가 안 붙는 컬럼"에만** 붙어 있다.
어디는 걸고 어디는 안 걸어도 되는지 알고 한 것이다.

**단, 함정이 하나 있다.** ✅ `ComposeJob` 주석이 스스로 경고하듯
**Hibernate의 `validate`는 인덱스를 검사하지 않는다** (테이블·컬럼·타입만 본다).
`@Index`를 적어도 기존 운영 DB에는 인덱스가 안 생긴다.
→ 개선 ③에서 `is_system` 인덱스를 걸 때 **운영 DB에서 `SHOW INDEX`로 확인**해야 한다.
