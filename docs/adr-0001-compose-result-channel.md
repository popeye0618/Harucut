# ADR-0001 · 합성 결과 통지 채널 — 왜 SQS인가

- **상태**: 제안됨 — [벤치마크](experiments/compose-result-channel-benchmark.md) 실행 후 "채택됨"으로 승격
- **날짜**: 2026-08-22 (같은 날 개정: C1'·C5·C6 후보 추가, 실패 분류 정교화)
- **관련**: PR #21 `feat/compose-async-invoke` (e29fae2), PR #19 `fix/compose-job-recovery` (153c35f)
- **비용 분석**: [합성 결과 통지 채널 비용 모델과 트레이드오프](compose-channel-cost-model.md)

## 0. 먼저 자리를 정확히 잡는다

"SQS 대신 Redis Stream이나 RabbitMQ를 쓰면 되지 않나"는 질문은 **SQS가 작업 큐 자리에
있다는 전제**를 깔고 있다. 그렇지 않다. 이 시스템에는 큐가 두 개 있고, 서로 다른 문제를 푼다.

```
[브라우저] --202--> [스프링 서버] --(1) 작업 큐--> compose_job 테이블
                          |
                          | (2) 비동기 invoke
                          v
                    [AWS Lambda] --결과 이미지--> S3
                          |
                          | (3) 결과 통지 채널  <-- 이 ADR의 주제
                          v
                    [스프링 서버] --DONE/FAILED--> compose_job 테이블
                          ^
                          | (4) 폴링
                    [브라우저]
```

- **(1) 작업 큐 = `compose_job` 테이블.** 2026-08-21(PR #19)에 이미 결정됐다.
  `started_at` 컬럼 + 조건부 UPDATE(`ComposeJobRepository.claim`)로 선점하고,
  `ComposeRerunScheduler`가 30초마다 버려진 PENDING을 다시 던진다.
  **이 자리는 브로커로 대체하지 않는다.** 내구성·멱등·다중 서버 안전이 이미 DB 트랜잭션
  안에서 해결됐고, 브로커를 넣으면 할 일 목록이 다시 두 군데로 쪼개진다 —
  PR #19가 고친 그 문제로 되돌아간다.
- **(3) 결과 통지 채널이 이 ADR의 주제다.** Redis Stream·RabbitMQ와 경쟁하는 자리는
  여기 하나뿐이다.

이 구분이 왜 중요한가: (3)의 **생산자는 AWS Lambda**다. 우리 네트워크 밖이다.
"서버와 같은 네트워크라 더 빠르다"는 장점이 이 구간에서는 성립하지 않는다.

## 1. 맥락 — 왜 통지 채널이 새로 필요해졌나

2026-08-21 측정 (Lambda reserved concurrency 30, 동시 18건):

| 항목 | 값 |
|---|---|
| 합성 1건 소요 | 8.3초 |
| 그중 Lambda 안에서 | 7.9초 (95%) |
| 성공 | 10건 |
| `429 Rate Exceeded`로 FAILED | 8건 |
| 그 8건이 회수됐나 | 아니오 — `findStalled`가 PENDING만 보므로 영구 FAILED |

동기 호출(`InvocationType.RequestResponse`)은 동시성 한도를 만나면 **밀리는 게 아니라
깨진다.** 그리고 요청 스레드는 7.9초 동안 소켓만 붙잡고 있다.

`InvocationType.EVENT`로 바꾸면 429가 Lambda 내부 재시도로 흡수된다. 대신
**호출의 응답이 더는 결과가 아니다.** 202(접수됨)만 돌아온다. 결과를 되받을 길을
새로 만들어야 한다 — 그게 (3)이다.

## 2. 제약은 어디에 걸리는가 — 세 층위

"Lambda에서 네트워크 통신으로 내 서버에 콜백하는 건 불가능한가"에 답하려면 세 층을 갈라야 한다.

### 1층 — 함수 코드 안에서 내 서버 호출: **제약 없다**

Lambda는 그냥 프로세스다. VPC에 넣지 않는 한 아웃바운드 인터넷이 열려 있어
HTTP POST도, Redis 연결도, RabbitMQ publish도 전부 된다. 후보 C1·C2가 이 층이다.
**여기에는 아무 제약이 없다.** 제약은 다음 층에만 있다.

### 2층 — Destinations의 직접 타깃: AWS 서비스로 묶인다

비동기 Lambda의 결과를 **함수 코드 밖에서** 받는 유일한 장치가 Destinations이고,
그 타깃은 AWS가 정해 놓았다:

| 타깃 | 우리 용도 |
|---|---|
| **SQS (standard)** | 서버가 끌어가는(pull) 내구성 큐 |
| SNS (standard) | **HTTPS 구독으로 내 서버에 직접 꽂을 수 있다** (→ 3층) |
| EventBridge | **API destination으로 내 서버에 직접 꽂을 수 있다** (→ 3층) |
| S3 | **실패 통지만** 가능. 성공 경로를 못 덮는다 |
| Lambda 함수 | 또 다른 함수가 서버를 불러야 한다 — 문제가 한 칸 밀릴 뿐 |
| ~~Redis Stream · RabbitMQ · HTTP 엔드포인트~~ | **직접 타깃으로는 못 넣는다** |

출처: [Capturing records of Lambda asynchronous invocations](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-retain-records.html)

### 3층 — 한 칸 끼우면 HTTP로 도달한다

**"AWS 서비스만 가능"은 정확하지 않다.** 릴레이를 하나 두면 함수 밖 관측을
유지하면서 내 서버가 HTTP로 직접 받을 수 있다. 실제로 성립하는 경로가 둘 있다.

| 경로 | 대가 |
|---|---|
| Destinations → **SNS → HTTPS 구독** → 내 서버 (C5) | 기본 재시도가 **3회**뿐이라 직접 늘려야 하고, 총 재시도 시간에 **3600초 하드 리밋**이 있다(연장 불가). 구독 확인 핸드셰이크 + 메시지 서명 검증. 소진되면 소실 — 막으려면 구독 DLQ, **그게 SQS다** |
| Destinations → **EventBridge → rule → API destination** → 내 서버 (C6) | 응답 **5초 타임아웃**(초과 시 실패 처리). 재시도는 24시간/185회로 넉넉. 구성요소 4개(bus·rule·connection·api destination) + Secrets Manager 시크릿. DLQ는 역시 SQS |

출처: [SNS message delivery retries](https://docs.aws.amazon.com/sns/latest/dg/sns-message-delivery-retries.html),
[API destinations as targets in EventBridge](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-api-destinations.html)

**따라서 진짜 축은 "AWS냐 아니냐"가 아니다. §4에서 그 축을 세운다.**

## 3. 실패를 분류한다 — 이게 후보를 가르는 기준이다

"함수가 죽으면 코드가 보고 못 한다"는 뭉뚱그린 말이다. 쪼개야 정확해진다.

| 실패 | 함수가 도나 | 함수 코드가 보고 가능한가 | Destinations |
|---|---|---|---|
| 스로틀 (429 / ZeroReservedConcurrency) | **아예 안 돈다** | **원천 불가** | OnFailure |
| EventAgeExceeded (수명 내 못 잡힘) | **아예 안 돈다** | **원천 불가** | EventAgeExceeded |
| 타임아웃 (60초 초과) | 돌다 죽는다 | `getRemainingTimeInMillis()` 워치독으로 T-2초에 자가 보고 **가능** | RetriesExhausted |
| OOM · 프로세스 강제 종료 | 돌다 죽는다 | `-Xmx`를 컨테이너 한도보다 낮추면 부분적으로 가능(불안정) | RetriesExhausted |
| 언핸들드 예외 | 돈다 | try/catch로 가능 | RetriesExhausted |
| 정상 실패(잘못된 입력 등) | 돈다 | 가능 | 통지 옴 |
| 성공 | 돈다 | 가능 | Success |

**위 두 줄이 결정적이다.** 함수가 실행조차 되지 않는 시간대라 어떤 코드 기법으로도
못 덮는다. 그리고 2026-08-21에 8건을 잃은 게 정확히 첫 줄이다.

동시에 3~4번째 줄은 **워치독으로 상당 부분 덮인다.** 이 문서의 초판은 이걸
"함수가 죽는 실패는 전부 못 보고한다"로 뭉쳐 C1을 실제보다 약하게 세웠다.
그래서 워치독 변형(C1')을 후보에 추가한다.

## 3.5 후보

### C0 — 동기 호출 유지 (기준선)

현행 main. 429로 깨지는 게 확인됐다. 기준선으로만 남긴다.

### C1 — HTTP 콜백: Lambda 함수 코드가 서버 엔드포인트를 호출

```
Lambda 코드 끝에서 POST /internal/compose/{jobId}/result
```

- **장점**: 인프라 0개 추가. 지연 최소. 실패 사유를 그대로 실어 보낸다.
- **대가**:
  - §3 표의 **위 두 줄을 원천적으로 못 덮는다.**
  - 서버가 재배포로 30초 내려가 있으면 그동안 온 통지는 사라진다.
    Lambda가 재시도하게 하려면 콜백 실패 시 함수를 실패로 끝내야 하는데,
    그러면 **이미 성공한 합성이 통째로 재실행된다.**
  - 인바운드를 외부에 열어야 한다 — 서명·재생 방지·멱등을 직접 만든다.

### C1' — C1 + 타임아웃 워치독

C1에 `getRemainingTimeInMillis()` 기반 워치독을 얹어, 남은 시간이 2초 이하로
떨어지면 "곧 타임아웃" 콜백을 먼저 쏘고 죽는다. §3 표의 3~4번째 줄을 부분적으로 덮는다.
**C1을 공정하게 평가하려면 이 변형으로 재야 한다.** 위 두 줄은 여전히 못 덮는다.

### C2 — Lambda 함수 코드가 Redis Stream에 XADD (또는 RabbitMQ publish)

- **장점**: 우리가 이미 Redis를 쓴다 (`spring-boot-starter-data-redis`, docker-compose의
  `redis:7-alpine`). 브로커 추가 없음. 통지 지연 최소.
- **대가**:
  - **C1과 같은 치명상** — §3 표의 위 두 줄.
  - **Lambda를 VPC에 넣어야 한다.** ElastiCache·RabbitMQ는 프라이빗 서브넷에 있다.
    ENI 할당이 붙고, S3 접근용 VPC 엔드포인트나 NAT 게이트웨이가 새로 필요하다
    (NAT는 시간당 과금 + 데이터 처리 과금).
  - 브로커 클라이언트가 함수 번들에 들어간다 → 콜드 스타트 증가.
  - 브로커 HA·영속성이 우리 책임. Redis Stream으로 at-least-once를 만들려면
    AOF/복제 설정과 pending entry 회수(`XAUTOCLAIM`)를 직접 운영해야 한다.

### C3 — Lambda Destinations → SQS **(현행 PR #21)**

- **장점**:
  - **함수 밖에서 관측한다.** 통지를 보내는 주체가 함수가 아니라 Lambda 서비스다.
    §3 표의 모든 행을 덮는다. `ComposeResultConsumer`가 `condition`으로 가른다:
    - `Success` → `completeJob`
    - `RetriesExhausted` → `failJob` (영구 실패)
    - **그 밖 → 아무것도 안 한다.** PENDING으로 두면 재실행 스케줄러가 다시 던진다.
  - **풀(pull)이다.** 서버가 자기 속도로 끌어간다 — 배압이 공짜다.
    재배포로 내려가 있어도 메시지는 큐에 남는다. 소비 중 프로세스가 죽으면
    가시성 타임아웃 뒤 재전달되고, 반복 실패는 DLQ로 간다.
  - 인바운드를 열지 않는다.
  - 완전관리형 — HA·영속성이 우리 운영 항목이 아니다.
- **대가**:
  - AWS 리소스 3개(큐·DLQ·Destination 설정)와 IAM 정책이 늘어난다.
  - 배포에 순서가 생긴다: AWS → Lambda → 서버. 그 사이 옛 서버(동기)와 새 서버가 공존한다
    (`ComposeResultConsumer.handle`의 `jobId == null` 분기가 이 공존 구간을 위한 것).
  - 통지 지연이 후보 중 가장 클 것으로 예상된다 (§4).
  - 롱폴링이 전용 스레드 하나를 상주시킨다.

### C4 — 통지를 안 받는다: 서버가 S3 결과 객체를 폴링

`compose_job`의 PENDING 행에 대해 `headObject(resultKey)`를 주기적으로 확인해
있으면 DONE으로 확정한다.

- **장점**: **제3의 서비스 0개.** 완전히 스프링 안에서 끝난다. 인바운드도 안 연다.
- **대가**:
  - **실패 사유가 사라진다.** 영구 실패와 처리 중을 구분할 수 없어
    `stale-after`(10분)를 다 기다린 뒤에야 FAILED를 찍는다.
  - 성공 확정이 폴링 주기만큼 늦다. 주기를 1초로 줄이면 `PENDING 건수 × 1 QPS`만큼
    S3 API 호출이 나간다.

### C5 — Destinations → SNS → HTTPS 구독 → 내 서버

- **장점**: **함수 밖 관측 + 내 서버가 직접 받는다.** §3 표를 전부 덮으면서
  큐 폴링 스레드가 없다. 지연이 C3보다 작을 가능성이 높다.
- **대가**:
  - **푸시다** — 서버가 살아 있어야 받는다.
  - 기본 재시도가 **3회**뿐이다. 늘릴 수 있지만 **총 재시도 시간 3600초가 하드 리밋**이다.
  - 소진되면 소실. 막으려면 구독 DLQ를 붙이는데 **그게 SQS다** — 신뢰성을 원하는 만큼
    C3로 수렴한다.
  - 인바운드 공개 + 구독 확인 핸드셰이크 + 메시지 서명 검증.

### C6 — Destinations → EventBridge → rule → API destination → 내 서버

- **장점**: C5와 같고, 재시도가 **24시간/185회**로 훨씬 넉넉하다. 인증(connection)이
  관리형이라 서명 검증을 직접 안 짜도 된다.
- **대가**:
  - **응답 5초 타임아웃.** `completeJob`은 DB 쓰기 + `UserMedia` 저장 + S3 삭제 예약을
    한다. 부하 상황에서 5초를 넘기면 성공 처리가 실패로 뒤집힌다 — **받자마자 큐잉하고
    즉시 200을 돌려주는 구조를 강제한다.** 그러면 내부에 또 큐가 생긴다.
  - 구성요소 4개 + Secrets Manager 시크릿. DLQ는 역시 SQS.
  - 여전히 푸시. 인바운드 공개.

## 4. 왜 "지연"으로 고르면 안 되는가

Redis Stream이 SQS보다 빠를 것이다. 그건 맞다. 그런데 그 이득이 어디로 가는지 보자.

| 구간 | 시간 |
|---|---|
| Lambda 안 (다운로드·렌더·업로드) | 7.9초 |
| 나머지 (invoke, 통지, DB 기록) | 0.4초 |
| **프론트 폴링 간격** | **1~2초** |

통지 채널이 20ms냐 300ms냐의 차이는 **전체의 3% 미만**이고, 그 앞에 폴링 주기
1~2초가 서 있어서 **사용자 체감에는 도달하지 못한다.** 사용자가 느끼는 지연은
폴링 주기가 지배한다 (→ [ADR-0002](adr-0002-compose-progress-delivery.md)).

**Redis Stream이 틀린 기술이라는 말이 아니다.** 자리가 다르다. Redis가 맞는 자리는
서버 ↔ 서버 팬아웃이고, 실제로 ADR-0002의 SSE 확장에서 그 자리가 나온다.

### 진짜 축: push vs pull

후보를 다 세워 놓고 보면 갈리는 선이 "AWS냐 아니냐"가 아니라 여기다.

| | 푸시 (C1, C1', C2, C5, C6) | 풀 (C3, C4) |
|---|---|---|
| 전제 | **서버가 지금 살아서 받을 수 있다** | 없음 |
| 전제가 깨지는 지점 | 재배포 30초(C1) · 3600초 하드 리밋(C5) · 응답 5초(C6) | — |
| 과부하 시 | 서버로 밀려든다 — 배압을 직접 만들어야 | 서버가 자기 속도로 끌어간다 |
| 인바운드 | 열어야 한다 | 안 연다 |
| 유실 방지 백스톱 | 재시도 정책 + DLQ = **결국 SQS** | 큐 자체 |

C5·C6는 "함수 밖 관측"과 "내 서버 직접 수신"을 둘 다 만족하는 진짜 후보다.
다만 신뢰성을 끝까지 밀면 DLQ로 SQS를 달게 되고, 그러면 **큐를 하나 두고 두 경로로
받는 구조**가 된다 — 정상은 HTTP, 실패는 큐. 그 복잡도가 지연 몇백 ms 값을 하는지가
C5·C6의 실제 쟁점이다.

---

## 5. "제3의 서비스 없이 스프링 안에서" — 어디까지 되나

**절반은 이미 그렇게 하고 있다.** 작업 큐(`compose_job` + `claim` + 30초 재실행 배치)는
브로커 없이 DB만으로 내구성·멱등·다중 서버 안전을 확보했다. 이건 되돌리지 않는다.

남은 건 통지 채널이고, 스프링만으로 가려면 **C4(S3 폴링)** 다. 가능하다.
바꿔 말해 SQS는 "없으면 안 되는 것"이 아니라 **"실패 사유와 즉시성을 사기 위해
관리형 큐 하나를 추가한 것"** 이다. 정직하게 그렇게 쓴다.

여기서 한 걸음 더 나가면 **Lambda 자체를 버리는 선택지**도 있다 (합성을 서버 인프로세스로
되돌리고 가상 스레드로 처리). 그러면 통지 채널 문제가 통째로 사라진다. 대가는
CPU 바운드 렌더링이 API 서버 코어를 먹는 것이고, 그게 실제로 얼마나 아픈지는
벤치마크의 F7 항목에서 잰다. 이 선택지를 명시적으로 재보지 않으면
"왜 Lambda인가"에 답이 없는 채로 "왜 SQS인가"만 답하는 꼴이 된다.

## 6. 결정

**C3 (Lambda Destinations → SQS)를 채택한다.** 근거는 이 순서다:

1. 비동기 invoke로 가야 한다 — 동기는 동시성 한도에서 깨진다(측정됨).
2. **배포할 때마다 확정적으로 유실된다.** 현재 배포는 docker-compose 단일 호스트라
   재기동 중 30초간 인바운드를 못 받는다. 푸시 중 재시도가 없는 C1·C1'·C2는
   **매 배포가 곧 유실**이다 (10만 건/월 기준 월 33건 ≈ 0.03%, 각각 최대 10분 대기).
   → [비용 모델 §7](compose-channel-cost-model.md)
3. 비동기의 실패를 **함수 밖에서** 관측해야 한다 — 함수 안에서 보고하는 방식(C1·C1'·C2)은
   **스로틀과 EventAgeExceeded를 원천적으로 못 덮는다**(§3). 워치독으로도 안 된다.
   함수가 실행조차 되지 않는 시간대이기 때문이다.
   (다만 비동기 전환으로 스로틀 자체가 드물어졌다 — 이 근거는 2번보다 약하다.)
4. 함수 밖 관측 = Destinations. 여기서 내 서버에 HTTP로 닿는 경로도 실재한다(C5·C6) —
   "AWS 서비스만 가능"은 사실이 아니다. 다만 셋 다 **푸시**라 "서버가 지금 받을 수 있다"를
   전제하고, 그 전제가 깨지는 지점을 재시도와 DLQ로 메워야 하며 **그 DLQ가 SQS다**.
5. C3는 **풀**이라 그 전제 자체가 없다. 배압이 공짜고 인바운드를 열지 않는다.
6. 지연도 요금도 결정 축이 아니다 — 지연 이득은 폴링 주기(1~2초) 뒤에 가려지고(§4),
   채널 간 요금 차이는 100만 건/월에서도 **월 $1.20**로 Lambda 컴퓨트($257)의 0.5% 미만이다.

**단, 이 ADR은 벤치마크 전까지 "제안됨"이다.** 다음 조건 중 하나라도 어긋나면 다시 연다:

- **무중단 배포(롤링·블루그린)를 도입한다** → 근거 2번이 사라진다. 남는 건 드문 스로틀뿐이라
  **C1'이 살아난다.** 현재 결정의 가장 큰 의존점이므로 배포 방식이 바뀌면 반드시 재검토한다
- 통지 채널 지연 p95 차이가 **500ms를 넘는다** → 지연이 결정 축으로 복귀
- **C1'(워치독)이 F2/F3(타임아웃·OOM)를 실용적으로 덮는다** → 남는 건 F4(스로틀)뿐이고,
  스로틀을 reserved concurrency 상향으로 없앨 수 있다면 C1'이 이긴다
- **C5 또는 C6의 유실률이 C3와 같으면서 지연이 유의미하게 낮다** → 푸시가 이긴다
- C4의 실패 사유 소실이 **실제 운영에서 문제가 안 된다** (예: 실패율이 0.1% 미만) →
  인프라 0개가 이긴다 (50줄, 개념 1개 — 규모가 작으면 이쪽이 맞다)

## 7. 이 결정에 딸린 것들

- **`compose.stale-after: 10m`은 Lambda `maximumEventAgeInSeconds=300` 전제 위에 있다.**
  기본값은 21600(6시간)이다. 설정을 빠뜨리면 아직 Lambda 큐에 살아 있는 이벤트를
  10분 뒤 다시 던져 같은 합성이 여러 번 돈다 (선점이 데이터는 지켜주지만 호출비는 두 번 나간다).
- 재실행 스케줄러는 SQS가 있어도 지워지지 않는다. 커밋 후 invoke 전에 서버가 죽는
  **이중 쓰기 구간**은 어떤 큐로도 못 막는다.
- SQS는 at-least-once다. 중복 통지는 `completeJob`의 `status != PENDING` 조기 반환이 흡수한다.
