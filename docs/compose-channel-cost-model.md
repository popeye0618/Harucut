# 분석 · 합성 결과 통지 채널 비용 모델과 트레이드오프

- **상태**: 분석 완료 (요율은 검증 필요 — §1)
- **날짜**: 2026-08-22
- **관련**: [ADR-0001](adr-0001-compose-result-channel.md), [벤치마크](experiments/compose-result-channel-benchmark.md)

---

## 0. 결론 먼저

**요금으로는 못 고른다.** 통지 채널 후보 사이의 AWS 요금 차이는 100만 건/월에서도
**최대 $1.20/월**이다. 같은 규모에서 Lambda 컴퓨트만 **$257/월**이 나간다.
채널 요금은 그 **0.5% 미만**이다.

지연으로도 못 고른다는 건 [ADR-0001 §4](adr-0001-compose-result-channel.md)에서 이미 봤다.
그러니 **지연도 요금도 결정 축이 아니다.** 남는 건 셋이다:

| 진짜 비용 | 어디서 나오나 |
|---|---|
| **코드** | 통지를 받고 검증하는 데 드는 줄 수 — SQS의 IAM을 HTTP는 서명·재생방지 코드로 대신 낸다 |
| **운영** | 장애 났을 때 알아야 하는 개념 수 |
| **유실** | 통지를 못 받은 1건 = 사용자가 8초 대신 **최대 10분** 대기 = 사실상 이탈 |

그리고 **유실 빈도를 지배하는 건 스로틀이 아니라 배포다.** 이게 이 분석의 핵심 발견이다.
스로틀은 비동기 전환으로 Lambda가 흡수하지만, 배포는 매일 있다.

## 3. 후보별 추가 AWS 요금

### C3 — SQS

두 갈래로 요청이 발생한다. **유휴 롱폴링이 통지보다 클 수 있다는 게 함정이다.**

- 통지당: `SendMessage`(Destination) 1 + `ReceiveMessage`(최대 10건 배치 → 0.1) + `DeleteMessage` 1 ≈ **2.1 요청**
- 유휴: 롱폴링 10초 → 6회/분 = **259,200 요청/월/인스턴스** (메시지가 0건이어도 발생)

| 규모 | 통지 요청 | 유휴(2인스턴스) | 총 | 과금분 | **비용** |
|---|---|---|---|---|---|
| 1만 | 21,000 | 518,400 | 539,400 | 0 | **$0** |
| 10만 | 210,000 | 518,400 | 728,400 | 0 | **$0** |
| 100만 | 2,100,000 | 518,400 | 2,618,400 | 1,618,400 | **$0.65** |

> 인스턴스를 4대까지 늘려도 유휴는 103만 요청/월이라 무료 티어를 겨우 넘는다.
> **롱폴링 유휴 비용은 실질적으로 0이다.** 대기 시간을 20초로 늘리면 절반이 된다.

### C1 / C1' — HTTP 콜백

**AWS 요금 $0.** 통지 페이로드가 KB 단위라 Lambda 아웃바운드 데이터 전송도
무료 구간(월 100GB) 안에 들어간다.

### C2 — Redis Stream

여기서 **NAT Gateway를 피할 수 있느냐가 요금을 가른다.**

| 구성 | 월 비용 | 비고 |
|---|---|---|
| Lambda VPC 배치 (ENI) | **$0** | ENI 자체는 무과금 |
| S3 접근 — **Gateway Endpoint** | **$0** | ✅ 확인됨. 이걸 쓰면 NAT가 필요 없다 |
| S3 접근 — NAT Gateway | **$32.85 + 데이터** | 시간당 $0.045 × 730h. 게이트웨이 엔드포인트로 **피할 수 있다** |
| Redis — 현재처럼 EC2의 docker 컨테이너 | **$0** | 단, **서버와 같은 호스트라 같이 죽는다** |
| Redis — ElastiCache t4g.micro 단일 | $12.41 | |
| Redis — ElastiCache HA (2노드) | **$24.82** | 통지 채널을 위해 브로커 HA를 사는 값 |

**제대로 구성하면 C2도 요금 $0이다.** NAT는 회피 가능하고, Redis는 이미 있다.
다만 "이미 있는 Redis"는 서버와 같은 호스트의 컨테이너라, **서버가 죽으면 통지도 같이
죽는다** — 통지 채널로서 의미가 없다. 의미를 가지려면 ElastiCache HA($24.82)로 분리해야 하고,
그러면 이 후보만 유일하게 기준선의 **9.7%**(100만 건 기준)를 쓴다.

### C4 — S3 폴링

HEAD 요청은 GET 요금이다. 주기가 전부다.

| 폴링 주기 | 건당 HEAD | 100만 건 비용 | 확정 지연 |
|---|---|---|---|
| 1초 | 8.3 | **$3.32** | ~0.5초 |
| 5초 | 1.7 | $0.66 | ~2.5초 |
| 30초 | 0.28 | ~$0.11 | ~15초 |

**요금과 지연이 정직하게 맞바꿔진다.** 그리고 어느 주기에서도 요금은 무시 가능하다.
C4의 진짜 대가는 요금이 아니라 **실패 사유 소실**이다.

### 종합 (100만 건/월)

| 후보 | 추가 요금 | 기준선($256.67) 대비 |
|---|---|---|
| C1 / C1' HTTP 콜백 | $0 | 0% |
| C2 Redis (EC2 컨테이너, NAT 회피) | $0 | 0% |
| C3 **SQS** | **$0.65** | **0.25%** |
| C5 SNS | $0.60 | 0.23% |
| C6 EventBridge | $1.20 | 0.47% |
| C4 S3 폴링 (1초) | $3.32 | 1.3% |

**통지 채널 요금 차이의 전체 폭이 월 $1.20다.** 커피 한 잔이다.
유일하게 유의미한 숫자(ElastiCache HA $24.82)는 통지 채널 비용이 아니라 브로커 운영 비용이고,
그건 C2를 **더 비싸게** 만든다.

## 4. 곁가지 — 그럼 Lambda는 왜 쓰나 (인프로세스와 비교)

통지 채널 논의의 전제가 "Lambda를 쓴다"이므로, 그 전제의 값도 재야 한다.
합성 1건의 CPU를 6초로 잡는다 (7.9초 중 S3 I/O 제외 추정).

| 규모 | vCPU-시간/월 | t3.medium 1대(1,460 vCPU-h/월) 대비 | Lambda 요금 |
|---|---|---|---|
| 1만 | 16.7 | 1.1% | $0 |
| 10만 | 166.7 | 11.4% | $19.67 |
| 100만 | 1,666.7 | **114%** — 한 대를 넘는다 | $256.67 |

**10만 건/월까지는 인프로세스가 요금상 공짜다.** 기존 서버의 여유 CPU에 들어간다.
100만 건이면 t3.medium 2대 추가(~$83/월)가 Lambda $256.67보다 **3배 싸다.**

그런데 이 표에 안 잡히는 게 둘 있다:

1. **피크/평균 비율.** 위 계산은 평균이다. 합성 트래픽은 저녁·주말에 몰릴 것이고,
   EC2는 피크에 맞춰 상시 사놔야 하지만 Lambda는 피크에만 낸다.
   피크가 평균의 5배면 EC2는 10대가 필요해져 우위가 사라진다.
2. **렌더링이 API와 코어를 다투는 비용.** 이건 요금이 아니라 p95로 나타난다.
   **벤치마크 F7이 정확히 이걸 잰다** — 아직 안 쟀다.

→ **"Lambda가 싸다"는 아직 증명되지 않았다.** F7 전에는 "Lambda가 격리와 탄력성을 준다"까지만
말할 수 있다. 10만 건/월 규모에서는 인프로세스가 요금상 더 유리하다는 걸 문서에 남긴다.

## 5. 코드 비용 (C3는 실측, 나머지는 추정)

**"인프라 0개니까 코드도 적을 것"이 틀렸다는 게 여기서 드러난다.**
SQS가 IAM으로 공짜로 받는 인증을, HTTP 후보는 서명·재생방지 코드로 직접 낸다.

| 후보 | 프로덕션 | 테스트 | 무엇이 드나 |
|---|---|---|---|
| **C3 SQS** | **~246줄** (실측) | 131줄 | `ComposeResultConsumer` 183 + `ComposeResultNotification` 38 + `SqsConfig` 18 + `AwsProperties` 7 |
| C1 / C1' | ~230줄 (추정) | ? | 컨트롤러 40 + DTO 30 + **HMAC 서명 검증 60** + **재생 방지(nonce·타임스탬프) 40** + 시큐리티 예외 10 + Lambda 쪽 클라이언트 50 (C1'은 워치독 +30) |
| C5 SNS | ~200줄 (추정) | ? | C1과 비슷하되 서명 검증은 SDK 유틸로 줄고, **구독 확인 핸드셰이크 30**이 붙는다 |
| C6 EventBridge | ~250줄 (추정) | ? | 인증은 관리형이라 서명 코드가 없지만, **5초 안에 200을 돌려주려면 받자마자 내부 큐에 넣어야 한다(+60)** |
| C2 Redis | ~200줄 (추정) | ? | 소비자 그룹 + **`XAUTOCLAIM` pending 회수 로직**이 SQS의 가시성 타임아웃을 대신한다 |
| **C4 S3 폴링** | **~50줄** | ~40줄 | 스케줄러 하나 + `headObject`. **압도적으로 적다** |

**C6의 아이러니**: 5초 타임아웃을 지키려고 받자마자 큐잉하면, **큐를 없애려던 후보가
내부에 큐를 만든다.** 그 큐는 인메모리라 프로세스가 죽으면 사라진다 —
PR #19가 고친 바로 그 문제다.

## 6. 운영 비용 — 장애 때 알아야 하는 개념 수

새벽에 알림을 받고 깨어난 사람이 알아야 하는 것들.

| 후보 | 개념 | 개수 |
|---|---|---|
| **C4** | S3 `headObject` | **1** |
| C1 / C1' | HMAC 서명, 재생 방지 윈도, 인바운드 방화벽 (+워치독) | 3~4 |
| C3 | 가시성 타임아웃, DLQ, 롱폴링, Destination `condition` | 4 |
| C2 | VPC/ENI, 소비자 그룹, `XAUTOCLAIM`, AOF·복제, 콜드스타트 | 5 |
| C5 | 구독 확인, 서명 검증, 재시도 정책 9속성, **3600초 하드 리밋**, 구독 DLQ | 5 |
| **C6** | bus·rule·connection·api destination, Secrets Manager, 5초 타임아웃, DLQ, 내부 큐 | **6+** |

C3의 4개는 전부 **AWS 콘솔에서 눈으로 확인 가능**하다(큐 깊이, DLQ 건수, 메시지 나이).
C1의 3개는 우리 로그에만 있다. C2의 `XAUTOCLAIM` pending 목록은 `redis-cli`를 쳐야 보인다.

**관측 가능성이 개수보다 중요하다.** 이건 표에 안 잡히는 C3의 이점이다.

## 7. 유실 비용 — 여기가 진짜 결정 지점

유실 1건 = 통지를 못 받음 = Job이 PENDING으로 남음 = 재실행 스케줄러가
`stale-after`(10분) 뒤 다시 던짐 = **사용자가 8초짜리 작업에 최대 10분을 기다림** = 이탈.

### 빈도를 지배하는 건 배포다

| 유실 원인 | 빈도 | C1/C1'/C2 | C3 | C5 | C6 |
|---|---|---|---|---|---|
| **배포 중 다운 30초** | **매일 1회** | **유실** | 생존(큐) | 생존(재시도) | 생존(재시도) |
| 스로틀 (429) | 드묾 — 비동기 전환으로 Lambda가 흡수 | 유실 | 생존 | 생존 | 생존 |
| EventAgeExceeded | 극심한 과부하만 | 유실 | 생존 | 생존 | 생존 |
| 서버 90분+ 장애 | 매우 드묾 | 유실 | 생존 | **유실**(3600초 리밋) | 생존 |
| 응답 5초 초과 | 부하 시 | — | — | — | **유실 위험** |

**정직하게 계산해 보자.** 10만 건/월 = 초당 0.038건. 배포 시 30초 다운이면
그 사이 완료되는 건 약 1.1건. 하루 1회 배포면 **월 33건 = 0.03%**.

**0.03%.** C1의 유실률은 생각보다 작다. 월 33명이 10분을 기다리는 게 허용 가능한가가
C1의 판정선이고, 그건 기술이 아니라 제품 판단이다.

### 그런데 조건이 하나 붙는다

위 계산은 **"배포하면 30초 내려간다"**를 전제한다. 무중단 배포(롤링·블루그린)를 하면
C1의 유실은 0에 수렴하고, **C1이 충분해진다.**

현재 배포는 docker-compose 단일 호스트다. `stop_grace_period: 60s`와 graceful shutdown이
있지만 그건 **진행 중 작업을 비우는 것**이지 무중단이 아니다 —
재기동 중에는 인바운드를 못 받는다.

> **→ 지금 이 인프라에서는 C1이 성립하지 않는다.**
> 그리고 이건 "SQS가 우월해서"가 아니라 **"우리가 아직 무중단 배포를 안 하기 때문"**이다.
> 이 문장이 ADR-0001에 빠져 있던 진짜 조건이다.

## 9. 규모별 권고 — 언제 답이 뒤집히나

**월 1만 건 미만 + 실패율이 낮고 실패 사유가 안 중요하면 → C4.**
50줄, 개념 1개, 요금 $0. SQS는 과잉이다. 대가는 확정이 폴링 주기만큼 늦고
실패 사유가 없다는 것뿐이고, 이 규모에서는 사람이 로그를 보면 된다.

**월 10만 건 + 무중단 배포가 있으면 → C1' 또는 C5.**
유실이 스로틀에만 남고 그건 드물다. 코드량이 C3와 비슷하니 인프라를 안 늘리는 쪽이 낫다.

**월 10만 건 + 무중단 배포가 없으면(현재) → C3.** ← 지금 여기
배포마다 확정적으로 유실되는 걸 막을 방법이 큐 말고 없다.

**월 100만 건 이상 → C3.**
배압이 공짜라는 게 그때부터 실제 값을 한다. 푸시 후보들은 전부
"과부하 시 서버로 밀려든다"를 직접 해결해야 한다.

**C6는 어느 규모에서도 권하지 않는다.** 개념 6개에 5초 타임아웃 때문에
내부 큐를 만들게 되는데, 그럴 거면 SQS를 쓰는 게 짧다.

**C2는 ElastiCache HA를 살 때만 의미가 있고, 그러면 유일하게 요금이 유의미해지는데
정작 스로틀 유실은 못 막는다.** 가장 나쁜 조합이다.

## 10. 이 분석이 ADR-0001에 더하는 것

1. **요금은 결정 축이 아니다** — 지연에 이어 두 번째로 탈락한 축.
   채널 전체 요금 폭이 월 $1.20다.
2. **C3의 진짜 근거는 "배포 중 유실"이다** — 스로틀이 아니다.
   스로틀은 비동기 전환이 이미 대부분 흡수했다.
3. **그 근거는 조건부다** — 무중단 배포를 도입하면 C1'이 살아난다.
   ADR-0001의 재검토 트리거에 **"무중단 배포 도입"**을 추가해야 한다.
4. **F7이 더 중요해졌다** — 10만 건/월에서 인프로세스가 요금상 공짜라면,
   "왜 Lambda인가"가 요금으로는 정당화되지 않는다. p95로 정당화해야 한다.
