## 버전 B — 문제/해결/성과 (포트폴리오 카드, 권장)

### 📌 문제 정의

사진 4장을 한 장으로 합성하는 API가 **건당 8.3초**(그중 렌더링 7.9초) 걸려
비동기로 접수(202)하고 폴링으로 결과를 주는 구조였다. 여기서 **작업이 조용히 사라지는**
두 종류의 유실이 발생했다.

| | 원인 | 증상 |
|---|---|---|
| **유실 ①** | 실행 트리거가 인메모리 이벤트 하나뿐이라, 스레드풀 큐 상한 초과·서버 종료·프로세스 사망 시 아무도 재개하지 않음 | 동시 30건 중 **26건이 영구 PENDING** |
| **유실 ②** | Lambda 동기 호출이 동시성 한도에서 `429`로 **예외를 던짐**. 워커가 FAILED로 기록했으나 재처리 배치는 PENDING만 조회 | 동시 30건 중 **9건(30%) 영구 실패, 회수 0건** |

두 경우 모두 클라이언트는 이미 **202를 받은 뒤**라 실패를 알 수 없었고,
멱등키로 재시도해도 기존 Job을 그대로 돌려받아 새 실행이 일어나지 않았다.

### 🔧 해결 과정

**1. 작업 큐를 휘발성 메모리에서 DB로 이전**
- `started_at` 컬럼 + **조건부 UPDATE 기반 선점**(영향 행 1이면 획득) → 다중 인스턴스 안전
- 30초 주기 재처리 배치: 미선점 건은 즉시, 실행 중 사망 건은 유예 시간 후 재투입
- graceful shutdown으로 정상 배포 시 큐를 비우고, 못 비운 꼬리는 배치가 회수 (예방/복구 분리)

**2. Lambda 호출을 동기 → 비동기(`InvocationType.EVENT`)로 전환**
- 동기 호출은 동시성 한도에서 **대기가 아니라 예외**를 던져 초과분이 손실됨
- 비동기 전환으로 초과분이 Lambda 내부 큐에서 대기·재시도되도록 변경
- 부수 효과로 `invoke`가 수십 ms로 끝나면서 전용 스레드풀과 `@Async` 제거

**3. 결과 통지 채널 선정 — 후보 6개 비교 후 SQS 채택**
- HTTP 콜백 / Redis Stream / SNS·EventBridge 릴레이 / S3 폴링 / SQS를 **지연·비용·유실률**로 비교
- **지연과 비용은 결정 축에서 탈락** — 채널 간 요금 차이 월 $1.20(Lambda 컴퓨트의 0.5% 미만),
  지연 차이는 폴링 주기 뒤에 가려짐
- 남은 축은 **"함수가 실행조차 되지 않는 실패를 관측할 수 있는가"**.
  스로틀·이벤트 만료는 함수 코드로 원천 보고 불가 → **Lambda Destination(함수 외부 관측)** 필요
- 서버가 끌어가는(pull) 방식이라 **과부하 시 배압이 자동 확보**되고 인바운드 노출 불필요

**4. 소비 방식·재시도 계층 정합성 확보**
- 숏폴링의 거짓 빈 응답(부분 샘플링) 회피를 위해 **롱폴링 상한 20초** 채택, 전용 스레드로 분리
- **재시도 계층이 두 개**(Lambda 이벤트 수명 / 서버 재처리 배치)임을 발견,
  겹치면 중복 실행되므로 `이벤트 수명 5분 + 함수 타임아웃 60초 + 여유 = 10분`으로 역산
- 실제 운영 설정이 **기본값 6시간**이었음을 발견하고 300초로 교정
- 미지의 실패 코드는 **"아무것도 하지 않고 PENDING 유지"**로 처리 → 재시도 가능한 실패의 영구 손실 방지

### 📈 성과

**개선 전후 이미지를 각각 빌드해 같은 환경에서 재측정** (동시 30건 · Lambda 동시 실행 한도 10)

| | 성공 | 영구 실패 | 전부 끝나기까지 |
|---|---|---|---|
| 개선 전 · 스레드 2 | 30건 | 0건 | 30초 |
| 개선 전 · 스레드 20 | 21건 | **9건 (30%)** | **10초** |
| **개선 후** | **30건** | **0건** | 53초 |

**스레드를 10배로 늘리면 3배 빨라지지만 30%를 잃는다.**
개선 후는 오히려 느려졌다 — 초과분을 버리는 대신 Lambda 내부 큐에 줄 세우기 때문이다.
**처리량을 산 것이 아니라 손실을 없앤 것이다.**

| 그 밖의 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 큐 상한 초과 시 영구 PENDING (동시 30건) | **26건** | **0건** |
| 배포 중 도착한 결과 통지 | 유실 | **큐가 버퍼링 → 유실 0** |
| 합성 워커 스레드 점유 | 건당 7.9초 블로킹 | **스레드풀 자체를 제거** |
| 통지 채널 추가 비용 | — | **월 $0.65** (100만 건 기준) |

**정성적 성과**
- 서버가 내려가 있어도 결과가 유실되지 않는 구조 확보 (푸시 → 풀 전환)
- 모든 실패 유형(타임아웃·OOM·스로틀·이벤트 만료)이 통지로 관측 가능해짐
- 4건의 아키텍처 결정을 **ADR로 문서화**하고, 각 결정에 **재검토 트리거를 수치로 명시**
- 개선 전 커밋으로 이미지를 따로 빌드해 **같은 환경에서 재현 가능한 비교 측정** 수행

## 버전 C — 면접 답변용 (2~3분 구술)

**"왜 SQS를 썼나요?"**

처음엔 저도 Redis Stream이 낫다고 생각했습니다. 이미 스택에 있었고 지연도 더 짧으니까요.
그런데 이 구간의 **생산자가 Lambda, 즉 저희 네트워크 밖**이라 "같은 네트워크라 빠르다"는
전제가 성립하지 않았습니다.

결정적이었던 건 **실패를 분류해본 것**입니다. 스로틀이나 이벤트 만료처럼
**함수가 실행조차 되지 않는 실패**는 함수 코드로는 원천적으로 보고할 수 없습니다.
타임아웃은 워치독으로 덮을 수 있지만 이 둘은 안 됩니다.
그래서 함수 밖에서 관측하는 Lambda Destination이 필요했고,
서버가 끌어갈 수 있는 내구성 타깃은 SQS였습니다.

지연과 비용은 **결정 축에서 지웠습니다.**
채널 간 요금 차이가 월 $1.20으로 Lambda 컴퓨트의 0.5% 미만이었고,
지연 차이는 프론트 폴링 주기 1~2초 뒤에 가려져 사용자에게 도달하지 않았거든요.
축을 하나씩 지우고 나니 **"함수가 안 돌았을 때도 알 수 있는가"** 하나만 남았습니다.

**"비동기로 바꿔서 처리량이 얼마나 늘었나요?"** (자주 나오는 함정 질문)

> ⚠️ **"몇 배 늘었다"고 답하면 안 된다.** 사실이 아니고, 되물으면 무너진다.

사실 **처리량은 늘지 않았습니다.** 병목이 저희 스레드가 아니라 Lambda 동시성 한도였거든요.
비동기가 한 일은 **초과분을 버리지 않고 줄 세운 것**입니다.
동기는 한도 초과분이 깨지고, 비동기는 대기합니다.

**측정하면 오히려 느려집니다.** 개선 전후를 같은 조건에서 다시 재봤는데,
동시 30건을 전부 끝내는 데 개선 전은 10초, 개선 후는 53초가 걸렸습니다.
대신 개선 전은 그 10초 동안 **9건(30%)을 영구히 잃었고**, 개선 후는 하나도 안 잃었습니다.

그 10초는 스레드를 2개에서 20개로 늘려서 얻은 숫자입니다.
스레드를 늘리면 처리량은 오르는데 **429를 더 자주 만나고,
동기 호출에서 429는 예외라서 그대로 영구 손실**이 됩니다.
**처리량과 손실률이 같이 올랐습니다.** 가상 스레드로 바꿔도 429는 그대로고요.

## 함께 쓸 만한 문장들

**한 줄 요약**
> 지연도 비용도 결정 축이 아니었다. 남은 축은 하나였다 —
> **함수가 실행조차 되지 않았을 때도 알 수 있는가.**

**배운 점 (자기소개서·회고용)**
1. **조용히 성공하는 실패가 가장 비싸다.** 202를 받고도 영원히 PENDING이었고,
   이벤트 수명이 6시간으로 잘못 잡혀 있어도 아무 에러가 나지 않았다.
2. **기본값은 결정이 아니라 위임이다.** 명시하지 않은 값은 환경이 대신 정한다.
3. **모르는 값은 안전한 쪽으로 떨어져야 한다.** 실패 코드를 enum이 아닌 String으로 받고
   미지의 값을 "건드리지 않음"으로 처리해, 미래의 신규 코드가 손실을 만들지 않게 했다.
4. **축을 지우는 것도 측정이다.** 무엇으로 고를지 정하는 데 절반의 시간을 썼다.
