# ADR-0003 · SQS 통지를 어떻게 소비하는가 — 전용 스레드 롱폴링

- **상태**: **채택됨** — §9 실행 항목 1~5 전부 적용 완료 (2026-08-22)
- **날짜**: 2026-08-22
- **관련**: [ADR-0001](adr-0001-compose-result-channel.md)(왜 SQS인가), `ComposeResultConsumer`

---

## 0. 먼저 — 지금 설정이 두 군데서 충돌하고 있다

| 어디 | 값 | 효력 |
|---|---|---|
| AWS 콘솔 (큐 속성 `ReceiveMessageWaitTimeSeconds`) | **20초** | **무시된다** |
| 코드 (`ComposeResultConsumer.WAIT_SECONDS`) | **10초** | **이게 실제 동작** |

**요청 파라미터가 큐 속성을 덮어쓴다.** AWS 문서가 숏폴링이 되는 조건을 이렇게 정의한다:

> 숏폴링은 `ReceiveMessage` 요청의 `WaitTimeSeconds`가 다음 두 방법 중 하나로 0일 때 발생한다:
> - `ReceiveMessage` 호출이 `WaitTimeSeconds`를 0으로 설정한다.
> - `ReceiveMessage` 호출이 `WaitTimeSeconds`를 설정하지 **않았고**, 큐 속성
>   `ReceiveMessageWaitTimeSeconds`가 0이다.
>
> — [SQS short and long polling](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-short-and-long-polling.html)

첫 번째 항목이 곧 우선순위다. 호출이 값을 주면 큐 속성은 안 본다.
코드가 `.waitTimeSeconds(WAIT_SECONDS)`를 항상 넘기므로 **콘솔의 20초는 죽은 설정**이다.

이 ADR은 두 가지를 정한다: **값을 얼마로 할 것인가**, 그리고 **어디를 단일 출처로 할 것인가.**

---

## 1. 왜 폴링(pull)인가

[ADR-0001 §4](adr-0001-compose-result-channel.md)에서 결정했다 — 요약하면 풀이라
"서버가 지금 살아서 받을 수 있다"는 전제가 없고, 과부하 시 배압이 공짜이며,
인바운드를 열지 않는다. 여기서는 **폴링을 어떻게 하느냐**만 다룬다.

---

## 2. 왜 숏폴링이 아니라 롱폴링인가

**이건 트레이드오프가 아니다. 롱폴링이 모든 축에서 이긴다.**

| | 숏폴링 (`wait=0`) | 롱폴링 (`wait>0`) |
|---|---|---|
| 큐가 빌 때 | 즉시 빈 응답 → **`sleep`으로 주기를 만들어야 한다** | 대기하다 만료 시 1회 응답 |
| 통지 지연 | **`sleep` 주기가 곧 지연** (1초 주기면 평균 0.5초) | 메시지 도착 즉시 반환 → **~0** |
| 거짓 빈 응답 | **있다** — 서버의 부분집합만 가중 무작위로 샘플링 | 없다 — **전 서버를 조회** |
| 유휴 요청/월/인스턴스 | 1초 주기 = **259만** | `wait=10` 기준 **25.9만** |
| 무료 티어(100만) | **초과 → 과금** | 안에 들어감 |

숏폴링의 "거짓 빈 응답"이 우리에게 특히 나쁘다. AWS 문서는 이렇게 쓴다:

> 큐의 메시지 수가 적으면(1,000 미만) 요청한 것보다 적게 받을 가능성이 높다.
> 메시지 수가 극히 적으면 특정 응답에서 **아무 메시지도 못 받을 수 있다.**

우리 큐가 정확히 그렇다 — 통지는 **드문드문 1건씩** 온다. 숏폴링이 가장 못 하는 모양이다.

> **결론**: `sleep` 주기를 짧게 해서 지연을 줄이면 요청 수가 폭증하고, 길게 하면 지연이 는다.
> 롱폴링은 **지연과 요청 수를 동시에 개선한다.** 고민할 게 없다.

## 3. 몇 초인가 — 10 vs 20

최대값은 **20초**다. 그 아래 값을 고르려면 그 값을 정당화하는 제약이 있어야 한다.
실제로 달라지는 건 셋뿐이다.

| 축 | `wait=10` | `wait=20` | 누가 이기나 |
|---|---|---|---|
| **통지 지연 (정상)** | ~0 | ~0 | **무승부** — 롱폴링은 메시지가 도착하면 즉시 반환한다. wait 값과 무관하다 |
| **유휴 요청/월/인스턴스** | 259,200 | **129,600** | 20 — 무료 티어(100만) 안에서 **3.8대 → 7.7대**까지 늘릴 수 있다 |
| **거짓 빈 응답 확률** | 상대적으로 높음 | **최소** | 20 — AWS: "**낮은 값**을 지정하면 드물게 메시지가 있어도 빈 응답을 받을 수 있다" |
| **종료 대기 상한** | **10초** | 20초 | 10 — `shutdownNow()`가 SDK 블로킹 호출을 즉시 못 깬다 |
| **소켓 타임아웃 여유** | 20초 | 10초 | 10 — SDK 기본 소켓 타임아웃 30초 아래여야 한다 |

### 통지 지연이 무승부인 게 핵심이다

흔한 오해가 "wait을 길게 하면 통지가 늦게 온다"인데, 반대다.
롱폴링은 **메시지가 도착하는 즉시 반환한다.** wait 값은 "메시지가 없을 때 얼마나 기다렸다
빈손으로 돌아올 것인가"일 뿐, 있는 메시지를 붙잡아 두지 않는다.
그래서 정상 경로에서 10이든 20이든 사용자 체감은 **똑같다.**

### 인스턴스 확장 여유는 실제 값이 있다

`application-load.yaml`에 이미 이렇게 적혀 있다:

```yaml
# 서버를 2대로 늘리는 순간(#2) 두 인스턴스의 숫자가 한 덩어리로 섞인다.
instance: ${INSTANCE_ID:app-1}
```

2대 계획이 문서화돼 있다. `wait=10`이면 3.8대에서 무료 티어를 넘고,
`wait=20`이면 7.7대까지 간다. 넘어도 요금은 미미하지만(월 $0.40/1M),
**늘릴 때 아무것도 안 건드려도 되는 여유**가 두 배다.

### 대가는 종료 10초뿐이다

코드는 종료 시 `awaitTermination(WAIT_SECONDS + 5)`로 기다린다 —
`wait=10`이면 15초, `wait=20`이면 25초다. `docker-compose.yml`의
`stop_grace_period: 60s` 안이고, 배포는 하루 1회다. **하루 10초.**

### 소켓 타임아웃은 상한을 설명해 준다

AWS 문서가 경고한다:

> HTTP 오류를 피하려면 `ReceiveMessage` 요청의 HTTP 응답 타임아웃이
> `WaitTimeSeconds`보다 길어야 한다.

AWS SDK v2의 동기 클라이언트(ApacheHttpClient) 기본 소켓 타임아웃이 30초다.
`SqsConfig`는 타임아웃을 재정의하지 않으므로 기본값을 쓴다.
`wait=20`이면 **10초 여유**가 남는다 — 안전하다. AWS가 상한을 20으로 잡은 이유이기도 하다.

> ⚠️ 나중에 누군가 `SqsClient`에 짧은 타임아웃(예: 15초)을 걸면 **롱폴링이 매번
> 타임아웃 예외로 끝난다.** 소비자는 5초 백오프 후 재시도를 반복하고, 겉보기엔
> "가끔 느린 것"처럼 보인다. `SqsConfig`에 이 제약을 주석으로 남겨야 한다.

## 4. 결정 ①: `wait = 20`

**롱폴링을 쓰는 목적 자체가 빈 응답과 거짓 빈 응답을 줄이는 것인데, 그 목적을 최대로
달성하는 값을 안 쓸 이유가 "배포가 하루 10초 길어진다"뿐이라면 목적이 이긴다.**

정직하게 반대 근거도 적는다: **거짓 빈 응답이 실제로 났을 때의 복구는 wait이 길수록
늦다.** 요청이 만료돼야 다음 요청을 걸기 때문에 최대 20초까지 늦어진다.
사용자가 1~2초 간격으로 폴링 중이라 20초 지연은 체감이 크다.
확률이 낮아지는 대신 발생 시 손해가 커지는 구조라, **어느 쪽 기댓값이 작은지는
문서로 알 수 없다.** → 벤치마크에 **"빈 응답 비율"**을 지표로 추가한다(§8).

## 5. 결정 ②: 단일 출처는 **코드**다

콘솔 값은 그대로 두되(코드가 덮으므로 무해하다), **값의 근거와 실제 동작은 코드에 둔다.**

- 콘솔 설정은 **코드 리뷰에 안 잡히고**, IaC도 없어서 누가 바꿔도 아무도 모른다.
- 코드에 있으면 `WAIT_SECONDS` 옆 주석이 곧 근거 문서가 된다.
- 대가: 값을 바꾸려면 재배포해야 한다. 이 값은 자주 바꿀 게 아니므로 받아들인다.

> 반대 선택(코드에서 파라미터를 빼고 큐 속성을 따르게 하기)도 성립한다 —
> 재배포 없이 튜닝할 수 있다. 하지만 그러면 **"코드를 봐도 몇 초인지 알 수 없다."**
> ADR-0002에서 SSE를 미룬 이유와 같은 종류의 판단이다: 숨은 결합보다 명시적 상수가 낫다.

## 6. 왜 전용 스레드인가 (`@Scheduled`가 아니라)

코드 주석에 이미 근거가 있다:

> `@Scheduled`가 아니라 전용 스레드인 이유: 롱폴링이 스레드를 10초씩 붙잡는다.
> 스케줄링 풀(4개)에 넣으면 배치들과 자리를 다투고, **그 결합이 설정 파일에 숨는다.**

보강하면, PR #19에서 `spring.task.scheduling.pool.size`를 올린 이유가
"기본 1이면 새벽 배치가 도는 동안 재실행이 굶는다"였다. 거기에 **20초씩 블로킹하는
작업을 하나 더** 넣으면 같은 문제가 재발하고, 이번엔 원인이 코드가 아니라
`application.yaml`의 숫자 하나에 숨는다. 풀 크기를 줄이는 순간 통지가 멈추는데
코드만 봐서는 알 수 없다.

`SmartLifecycle`의 기본 phase(`Integer.MAX_VALUE`)를 그대로 쓰는 것도 의도적이다.
스프링은 **높은 phase부터 멈추므로** 소비자가 가장 먼저 멈추고 DB·커넥션 풀이 그 뒤에
내려간다. 순서가 반대면 처리 중이던 통지가 죽은 커넥션을 잡는다.

## 7. 왜 직접 짰나 (`@SqsListener`가 아니라)

Spring Cloud AWS의 `@SqsListener`를 쓰면 183줄 대부분을 안 짜도 된다.
안 쓴 이유와 그 대가를 정직하게 적는다.

**안 쓴 이유:**
- **의존성.** 지금은 순수 AWS SDK(`software.amazon.awssdk:sqs`)만 쓴다.
  Spring Cloud AWS는 별도 BOM과 버전 정렬이 필요하고, **Boot 4.1 대응 여부를 확인해야 한다** —
  springdoc에서 이미 "2.x는 Boot 3 전용이라 여기서는 안 뜬다"를 겪었다(`build.gradle` 주석).
- **동작이 보인다.** 가시성 타임아웃 활용, 삭제 시점, 에러 백오프, 종료 순서가 전부
  우리 코드 한 파일에 있다. 장애 때 읽을 곳이 한 군데다.
- **줄여주는 게 수신 루프뿐이다.** `condition` 분기(Success / RetriesExhausted / 그 외)는
  어차피 우리가 짜야 한다. 그게 이 소비자의 본질이고 프레임워크가 대신해 주지 않는다.

**대가:**
- 183줄을 우리가 유지한다.
- 병렬 소비, 배치 삭제(`DeleteMessageBatch`), 지수 백오프를 나중에 원하면 직접 만든다.

**재검토 트리거**: 순차 1건 처리로 통지가 밀리기 시작할 때. 지금은 배치 10건을 받아
한 건씩 처리하고 한 건씩 지운다.

## 8. 같이 정해야 하는데 아직 안 정한 것들

| 항목 | 지금 | 문제 |
|---|---|---|
| **가시성 타임아웃** | **코드에서 안 정한다 → 큐 기본값 30초** | `completeJob`이 30초를 넘기면 같은 통지가 다시 온다. `status != PENDING` 조기 반환이 흡수하지만, **기본값에 의존하고 있다는 사실이 어디에도 안 적혀 있다.** 콘솔에서 누가 바꿔도 모른다 |
| `MAX_MESSAGES = 10` | SQS 최대값 | 적절하다. 통지가 몰릴 때 요청 수가 최대 1/10이 된다 |
| 삭제 시점 | **처리 성공 후에만** | 의도적이다. 실패 시 안 지우면 가시성 타임아웃 뒤 재전달되고, 반복 실패는 DLQ로 간다 |
| 에러 백오프 | 5초 고정 | 자격증명 만료·네트워크 단절 같은 지속 실패에서 뜨거운 루프를 막는다. 지수 백오프는 아직 필요 없다 |
| 처리 동시성 | 순차 1건 | 통지 처리가 DB 트랜잭션 하나라 짧다. 지금은 충분하다 |

## 9. 실행 항목 — 전부 완료 (2026-08-22)

1. ✅ `ComposeResultConsumer.WAIT_SECONDS` **10 → 20**, 근거를 상수 옆 주석으로
   (지연은 무승부, 요청 수 절반, 거짓 빈 응답 최소, 대가는 종료 10초).
2. ✅ `SqsConfig`에 **"타임아웃을 재정의하려면 `WAIT_SECONDS`보다 길어야 한다"** 주석.
   증상이 "가끔 느린 것"으로 보인다는 점까지 적었다.
3. ✅ **가시성 타임아웃을 `VISIBILITY_TIMEOUT_SECONDS = 30`으로 명시**하고
   `ReceiveMessage`마다 넘긴다. 큐 기본값과 같은 값이지만, 암묵적 의존을 없앴다.
4. ✅ `compose-lambda/README.md`에 큐·DLQ·IAM·Destination 생성 절차를 추가하고,
   **"큐 속성은 코드에 덮인다"**를 명시했다. 그 문서에 남아 있던 옛 설계
   (동기 호출, `COMPOSE_EXECUTOR` 스위치, 인프로세스 기본값)도 같이 정정했다.
5. ✅ 벤치마크 측정 A에 **빈 응답 비율**을 지표로 추가 — 정상 빈 응답과 거짓 빈 응답을
   구분해 세는 방법까지 적었다.

> §4의 반대 근거(거짓 빈 응답 시 복구가 최대 20초)는 **아직 검증되지 않았다.**
> 5번 지표가 실측되기 전까지 이 ADR의 값 선택은 논증이지 측정이 아니다.

## 10. 재검토 트리거

- 인스턴스가 **8대**를 넘는다 → 유휴 요청이 무료 티어를 넘는다(요금은 여전히 미미하지만
  그때 wait 값과 인스턴스 수의 관계를 다시 계산한다)
- **빈 응답 비율이 유의미하게 높다** → wait을 20으로 올린 판단이 틀렸을 수 있다
- 통지 처리가 순차로 밀린다 → 병렬 소비 또는 `@SqsListener` 도입 검토
- `SqsClient`에 타임아웃을 재정의할 일이 생긴다 → §3의 소켓 타임아웃 제약을 반드시 확인
