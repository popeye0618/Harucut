# ADR-0002 · 합성 진행 전달 — 202 + 폴링을 유지하고 SSE를 미룬다

- **상태**: 제안됨
- **날짜**: 2026-08-22
- **관련**: [ADR-0001](adr-0001-compose-result-channel.md), `ComposeController`

---

## 0. 먼저: SSE는 SQS의 대안이 아니다

두 질문이 자주 붙어 다니는데 구간이 다르다.

```
[Lambda] --(3) 결과 통지--> [서버] --(4) 진행 전달--> [브라우저]
            ADR-0001                    ADR-0002
         SQS / Redis / 콜백          폴링 / SSE / WS / 푸시
```

SSE를 도입해도 (3)은 그대로 필요하다. SSE로 SQS를 대체할 수는 없다.
이 ADR은 (4)만 다룬다.

---

## 1. 왜 202인가 (이건 폴링/SSE와 별개 축)

합성은 8.3초 걸린다. 이걸 HTTP 요청 하나로 붙잡고 있으면:

- **프록시·ALB idle timeout**에 걸린다. 콜드 스타트가 겹치면 더 길어진다.
- **모바일 네트워크 전환**(LTE↔WiFi)에서 연결이 끊긴다. 작업은 서버에서 계속 도는데
  클라이언트는 결과를 잃는다.
- 끊긴 클라이언트가 **재시도하면 중복 실행**이 된다. 지금은 `idempotencyKey`가 막지만,
  애초에 그 압력을 만들 이유가 없다.
- 8.3초 × 동시 요청수만큼 커넥션을 점유한다.

**202는 유지한다.** 이 부분은 재검토 대상이 아니다.
쟁점은 "그 다음 결과를 어떻게 전달하느냐"뿐이다.

---

## 2. 폴링의 실제 비용

현행: `GET /api/auth/user/media/compose/{jobId}`를 1~2초 간격.

| 항목 | 값 |
|---|---|
| 작업 1건당 폴링 횟수 | 8.3초 ÷ 1.5초 ≈ **6회** |
| 1회당 서버 작업 | JWT 검증 + `findByIdAndUser` PK 조회 1건 |
| 결과 인지 지연 (폴링 주기의 절반) | 평균 **0.75초** |

**작업 하나에 6번.** 이게 이 ADR의 핵심 숫자다.

---

## 3. 후보

### P1 — 폴링 유지 (현행)

- **장점**: 상태가 없다. 인스턴스 몇 대든 아무 데나 가면 된다. 프론트는 재접속 로직이
  필요 없고, 앱을 백그라운드에 뒀다 돌아와도 그냥 다시 물어보면 된다.
  실패 경로가 성공 경로와 같다.
- **대가**: 요청 6배, 결과 인지가 평균 0.75초 늦다.

### P2 — SSE (`SseEmitter`)

- **장점**: 완료 즉시 전달(0.75초 제거), 요청 6회 → 1회.
- **대가**:
  - **다중 인스턴스에서 그냥 깨진다.** SQS 통지를 받은 인스턴스와 브라우저의 SSE 연결이
    붙은 인스턴스가 다를 수 있다. 통지를 받은 쪽이 연결을 가진 쪽에 알려야 한다 →
    **Redis Pub/Sub 팬아웃이 필요하다.** "제3의 서비스를 줄이자"와 정확히 반대 방향이다.
    (Redis는 이미 스택에 있으니 실현은 가능하다 — 여기가 Redis가 맞는 자리다.)
  - **폴링 경로를 지울 수 없다.** 연결이 끊기는 동안 완료된 이벤트를 어떻게 따라잡을
    것인가는 SSE가 답해주지 않는다. `Last-Event-ID`를 구현하든, 재접속 시 현재 상태를
    한 번 조회하든 — 후자가 곧 폴링 엔드포인트다. **두 경로를 다 유지하고 다 테스트해야 한다.**
  - 프록시가 SSE를 버퍼링하지 않도록 설정해야 하고, idle timeout보다 짧은 주기로
    heartbeat를 보내야 한다.
  - 커넥션이 작업이 끝날 때까지 살아 있다 (서블릿 비동기라 스레드는 안 잡지만
    커넥션·`SseEmitter` 인스턴스는 잡는다). 동시 대기 건수만큼 열린 연결이 쌓인다.

### P3 — WebSocket

P2의 비용을 전부 지고 양방향까지 얹는다. 우리는 서버→클라이언트 단방향 통지 하나만
필요하다. **과하다.** 후보에서 제외한다.

### P4 — 푸시 알림 (FCM/APNs)

앱을 닫아도 도달한다는 게 유일한 강점이다. 8초짜리 작업에 사용자가 앱을 닫고 있을
이유가 별로 없다. 다만 합성이 **분 단위로 길어지는 미래**(고해상도·다중 프레임 일괄)가
오면 이게 정답이 된다. 지금은 아니다.

---

## 4. 결정

**P1(폴링)을 유지한다.**

작업 하나에 6번의 가벼운 요청이 SSE의 복잡도 — Redis 팬아웃 + 재접속 처리 +
프록시 설정 + 지우지 못하는 폴링 폴백 — 를 정당화하지 못한다.
SSE가 사는 이득은 **평균 0.75초**인데, 그 앞에 8.3초짜리 합성이 서 있다. 9% 개선이다.

## 5. 언제 다시 연다 — 선을 미리 긋는다

다음 중 **하나라도** 넘으면 이 ADR을 다시 연다. 사후에 기준을 만들지 않기 위해 지금 적는다.

| 트리거 | 임계 | 왜 이 값인가 |
|---|---|---|
| 폴링이 전체 요청에서 차지하는 비중 | **15% 초과** | 그 아래면 API 서버 용량 계획을 바꾸지 않는다 |
| 합성 소요 p95 | **20초 초과** | 폴링 횟수가 13회를 넘어 "6번"이라는 근거가 무너진다 |
| 동시 대기(PENDING) 건수 p95 | **200 초과** | 폴링 QPS ≈ 133 — 단일 인스턴스에서 유의미해지는 지점 |
| 사용자 체감 지연 불만 | 정성 | 0.75초가 실제로 문제로 보고되면 |

이 지표들은 이미 붙어 있는 관측 스택(Prometheus + Grafana, PR #20)에서 뽑는다.
합성 관련 대시보드에 위 4개를 패널로 올리는 게 이 ADR의 실행 항목이다.

## 6. 다시 열 때의 전제조건

SSE로 갈 때 반드시 같이 결정해야 하는 것들. 지금 안 정하면 그때 급하게 정하게 된다.

1. **팬아웃**: Redis Pub/Sub. 통지를 받은 인스턴스가 `compose:job:{jobId}` 채널에 publish하고,
   연결을 가진 인스턴스가 구독한다.
2. **폴백 유지**: 폴링 엔드포인트는 남긴다. SSE 연결 실패·재접속 시 현재 상태를 한 번 조회한다.
   프론트 계약은 "SSE를 우선 쓰되, 끊기면 폴링"이다.
3. **연결 상한**: 인스턴스당 동시 `SseEmitter` 수에 상한을 두고, 넘치면 폴링으로 되돌린다.
   상한이 없으면 트래픽 급증이 커넥션 고갈로 번진다.
4. **타임아웃**: `SseEmitter` 타임아웃은 `compose.stale-after`(10분)보다 짧게. 끝나지 않는
   작업에 연결을 무한정 붙잡아 두지 않는다.

## 7. 지금 당장 할 수 있는 값싼 개선

SSE 없이도 체감 지연을 줄일 수 있다. 채택 전에 먼저 재볼 것:

- **폴링 간격을 적응형으로.** 첫 5초는 2초 간격(어차피 안 끝난다), 이후 0.5초.
  총 요청 수는 비슷한데 인지 지연은 0.75초 → 0.25초로 줄어든다.
- **긴 폴링(long polling).** 상태 조회를 최대 3초까지 붙잡았다가 변화가 있으면 즉시 응답.
  SSE 이득의 대부분을 가져오면서 팬아웃이 필요 없다 — 단, 인스턴스가 여러 대면
  통지를 받은 인스턴스가 아닌 곳에서 대기 중일 수 있으므로 DB를 짧게 재조회하는
  방식이어야 한다. 커넥션 점유는 SSE와 같은 성질의 비용이다.

둘 다 프론트/서버 변경이 작다. **SSE를 검토하기 전에 이 둘을 먼저 잰다.**
