# 실험 · 합성 결과 통지 채널 벤치마크

- **상태**: 설계됨, **미실행**
- **목적**: [ADR-0001](../adr-0001-compose-result-channel.md)의 후보를 숫자로 가른다
- **날짜**: 2026-08-22 (같은 날 개정: C1'·C5·C6 추가, F2/F3 예상 수정)

---

## 0. 이 실험이 반드시 피해야 하는 것

"SQS를 이미 붙였으니 SQS가 이기는 측정을 한다"가 되면 아무 가치가 없다.
그래서 **판정 기준과 예상 결과를 실행 전에 여기 못 박는다.** 실행 후 기준을
고치려면 고친 사실과 이유를 문서에 남긴다.

그리고 **처리량·지연으로 재면 SQS는 이기지 않는다.** Redis Stream이 더 빠를 것이다.
지연으로 SQS를 정당화하려 들면 그 서사는 거짓이 된다.
이 실험이 재려는 것은 **"통지가 오지 않는 상황이 얼마나 있고, 그때 무슨 일이 나는가"**다.

**후보를 약하게 세우지 않는다.** 초판 설계는 C1(HTTP 콜백)을 워치독 없이 세워
타임아웃·OOM에서 자동으로 지게 만들어 놨었다. 그건 측정이 아니라 연출이다.
C1'을 추가해 C1이 낼 수 있는 최선으로 붙인다.

## 1. 후보 (ADR-0001 §3.5)

| 코드 | 구성 | 방향 | 구현 비용(추정) |
|---|---|---|---|
| **C0** | 동기 invoke (현행 main) — 기준선 | — | 0 (이미 있음) |
| **C1** | Lambda 코드 → HTTP 콜백 `POST /internal/compose/{jobId}/result` | push | 서버 엔드포인트 + 서명 검증 + Lambda 클라이언트 |
| **C1'** | C1 + `getRemainingTimeInMillis()` 워치독 (T-2초 자가 보고) | push | C1 + 워치독 스레드 |
| **C2** | Lambda 코드 → Redis Stream `XADD` (Lambda를 VPC에 배치) | push | VPC/ENI/S3 엔드포인트 + Lettuce 번들 + 소비자 그룹 |
| **C3** | Lambda Destinations → SQS (현행 PR #21) | **pull** | 0 (이미 있음) |
| **C4** | 통지 없음 — 서버가 S3 `headObject` 폴링 | **pull** | 스케줄러 하나 |
| **C5** | Destinations → SNS → HTTPS 구독 → 내 서버 | push | SNS 토픽 + 구독 확인 + 서명 검증 + 재시도 정책 튜닝 |
| **C6** | Destinations → EventBridge → rule → API destination → 내 서버 | push | bus·rule·connection·api destination + Secrets Manager |

> C2를 RabbitMQ로 바꾼 변형(C2')은 **돌리지 않는다.** Redis가 이미 스택에 있어
> C2가 C2'의 상한이기 때문이다 — C2가 지면 C2'는 볼 것도 없이 진다.

## 2. 환경

- 서버: docker-compose (mysql 8.0, redis 7) + `application-load.yaml`
- Lambda: 실제 AWS. `reserved concurrency = 30`, timeout 60s,
  `maximumEventAgeInSeconds = 300`, `maximumRetryAttempts = 2`
- 관측: 기존 Prometheus + Grafana 스택 (PR #20)
- **LocalStack을 쓰지 않는다.** 이 실험의 주제가 스로틀·타임아웃·Destination 전달 같은
  AWS 고유 실패 동작이라, 에뮬레이터로 재면 재는 대상이 사라진다.

### 계측 지점

세 시각을 각각 남긴다. 이게 없으면 채널 몫만 떼어낼 수 없다.

| 기호 | 무엇 | 어디서 |
|---|---|---|
| `t0` | 서버가 invoke 호출 | `LambdaComposeExecutor.execute` |
| `t1` | Lambda가 S3 업로드 완료 | `ComposeHandler` 로그 (CloudWatch) |
| `t2` | 서버가 DONE/FAILED 기록 | `ComposeService.completeJob` / `failJob` |
| `t3` | 프론트가 상태 변화를 인지 | 부하 스크립트의 폴링 루프 |

**채널 지연 = `t2 - t1`.** 이게 후보를 직접 비교하는 값이다.
`t3 - t2`는 폴링 주기가 지배하므로 [ADR-0002](../adr-0002-compose-progress-delivery.md)의 몫이다.

## 3. 측정 A — 정상 경로

부하: 동시 **18건**(2026-08-21 측정 재현), **100건**, **300건**.

| 지표 | 왜 재나 |
|---|---|
| 채널 지연 `t2-t1` p50/p95/p99 | 후보 간 직접 비교 |
| 전체 소요 `t2-t0` p50/p95 | 사용자 체감의 상한 |
| 성공률 | C0가 여기서 깨지는 걸 재현한다 |
| 서버 CPU / 커넥션 / 스레드 | C3의 롱폴링 상주 스레드, 푸시 후보의 인바운드 비용 |
| Lambda 콜드 스타트 p95 | C2의 VPC ENI + 번들 증가분 |
| **C6의 응답 시간 p99** | **5초 타임아웃에 얼마나 붙는지** — 300건에서 위험 |
| **C3의 빈 응답 비율** | `ReceiveMessage`가 0건으로 돌아온 비율. [ADR-0003 §4](../adr-0003-sqs-consumption.md)의 반대 근거를 검증하는 **유일한 방법**이다 — 롱폴링 20초는 거짓 빈 응답 확률을 낮추는 대신 발생 시 복구를 최대 20초까지 늦춘다. 큐가 비어 있어서 온 빈 응답(정상)과 **메시지가 있는데 온 빈 응답**(거짓)을 구분해서 세야 한다: 빈 응답 직후 재요청이 즉시 메시지를 받으면 그 앞 응답이 거짓이었다는 뜻이다 |

### 예상 (실행 전에 적는다)

```
채널 지연 p95:  C2(Redis) < C1/C1'(HTTP) < C5(SNS) ~ C6(EB) < C3(SQS) < C4(S3 폴링)
                ~20ms       ~30ms           ~100ms          ~200-500ms   ~주기의 절반
```

**판정 기준 ①**: 가장 빠른 후보와 C3의 채널 지연 p95 차이가 **500ms 이내**면,
전체 8.3초 대비 6% 미만이고 폴링 주기(1~2초) 뒤에 가려지므로
**지연을 결정 축에서 제외한다.** 500ms를 넘으면 지연이 축으로 복귀하고
ADR-0001을 다시 연다.

## 4. 측정 B — 장애 주입 (이 실험의 본체)

각 셀에 네 가지를 기록한다: **통지 도착 여부 / Job 최종 상태 / 실패 사유 보존 / TTR**
(TTR = 요청부터 최종 확정까지, 재실행 배치 대기 포함).

| | 주입 방법 | C0 | C1 | C1' | C2 | C3 | C4 | C5 | C6 |
|---|---|---|---|---|---|---|---|---|---|
| **F1** 서버 재배포 중 통지 도착 | 컨테이너 30초 정지 후 재기동 | | | | | | | | |
| **F2** Lambda 타임아웃 | 핸들러에 70초 sleep 주입 (timeout 60s) | | | | | | | | |
| **F3** Lambda OOM | 큰 배열 할당으로 메모리 한도 초과 | | | | | | | | |
| **F4** 동시성 스로틀 | reserved concurrency 2 + 동시 50건 | | | | | | | | |
| **F5** 통지 처리 중 서버 사망 | 소비/수신 진입 후 `kill -9` | | | | | | | | |
| **F6** 브로커 재시작 | Redis 컨테이너 restart (C2만) | — | — | — | | — | — | — | — |
| **F7** 렌더링 중 API 응답 저하 | 합성 30건 동시 + 다른 API p95 측정 | | | | | | | | |
| **F8** 서버 장기 다운 | 컨테이너 90분 정지 (C5의 3600초 리밋 검증) | — | | | — | | — | | |

> **F7은 후보 비교가 아니다.** "왜 Lambda인가"를 재는 항목이다.
> 인프로세스 합성(`InProcessComposeExecutor`, PR #21에서 삭제됨)을 임시로 되살려
> 같은 부하를 주고 다른 API의 p95 상승폭을 잰다. 이게 크지 않다면
> Lambda도 SQS도 필요 없다는 뜻이 되므로, **가장 먼저 돌려야 하는 항목이다.**

> **F8은 C5를 위해 새로 넣었다.** SNS의 총 재시도 시간 3600초는 하드 리밋이라
> 늘릴 수 없다. 90분 다운이면 재시도가 소진되고, DLQ가 없으면 통지가 사라진다.
> C6(24시간)와 C3(큐 보존 기간)는 살아남아야 한다.

### 예상 (실행 전에 적는다)

- **F2·F3**: C1·C2는 **통지 0건**. C1'은 **F2를 부분적으로 덮는다**(워치독이 T-2초에
  쏜다) — 이게 초판 예상에서 바뀐 부분이다. F3(OOM)은 컨테이너가 SIGKILL되면
  워치독도 못 돈다. C3·C5·C6는 `RetriesExhausted` 통지가 실패 사유와 함께 도착.
  C4는 실패를 성공과 구분 못 해 10분 뒤 사유 없이 FAILED.
- **F4 (핵심)**: C0는 8/18을 **영구 FAILED**로 잃는다(2026-08-21 재현).
  **C1·C1'·C2는 통지 0건 — 워치독으로도 못 덮는다.** 함수가 실행조차 되지 않는다.
  C3·C5·C6는 Lambda 내부 재시도로 흡수되거나 `EventAgeExceeded`로 와서 PENDING 유지.
- **F1**: C1·C1'은 **유실**(서버가 없는 동안 온 콜백은 사라진다).
  C5는 재시도가 30초를 덮으므로 생존. C6도 생존. C2는 브로커에 남으므로 생존.
  C3는 큐에 남아 생존. C4는 애초에 통지가 없어 영향 없음.
- **F5**: C3는 가시성 타임아웃 뒤 재전달 → 생존. C5·C6는 5xx를 반환하지 못하고
  죽으므로 재시도 대상이 되어 생존. C2는 pending entry를 `XAUTOCLAIM`으로
  회수하는 코드를 우리가 짜야 생존.
- **F8**: C5 **유실**(3600초 리밋). C6·C3 생존.

**판정 기준 ②**: **F4에서 통지가 0건인 후보는 탈락한다.**
스로틀은 함수가 실행조차 되지 않는 시간대라 어떤 코드 기법으로도 못 덮고,
2026-08-21에 실제로 8건을 잃은 모드다. → C1·C1'·C2 탈락 예상.

**판정 기준 ③**: 유실되는 후보는 **TTR을 반드시 기록한다.**
재실행 배치가 결국 회수하더라도 10분이다. 8초짜리 작업에 10분을 물릴 수 있는가가
살릴지 죽일지를 정한다.

**판정 기준 ④**: C5·C6가 **DLQ 없이** F1·F5·F8을 전부 통과하면 푸시가 이긴다.
DLQ를 붙여야만 통과한다면, 그건 "SQS를 쓰면서 HTTP 경로를 하나 더 얹은 것"이므로
C3보다 복잡하다 — 탈락.

## 5. 측정 C — 비용과 운영

| 항목 | C1' | C2 | C3 | C4 | C5 | C6 |
|---|---|---|---|---|---|---|
| 월 AWS 요금 (10만 건/월 가정) | | | | | | |
| 새로 생기는 인프라 | 없음 | VPC/ENI/NAT, Redis HA | SQS + DLQ | 없음 | SNS(+DLQ) | bus·rule·connection·api dest(+DLQ) |
| 우리가 지는 운영 책임 | 인바운드 보안 | 브로커 HA·영속성·pending 회수 | 없음 | 없음 | 인바운드 보안 + 서명 검증 | 인바운드 보안 |
| 배포 단계 수 | 2 | 3 | 3 | 1 | 3 | 3 |
| 롤백 난이도 | | | | | | |

NAT 게이트웨이는 시간당 + 데이터 처리 과금이라 C2에서 **트래픽과 무관한 고정비**가
생긴다. S3 게이트웨이 엔드포인트로 피할 수 있는지 함께 확인한다.

## 6. 실행 순서

1. **F7 먼저.** 인프로세스 합성이 API에 미치는 영향을 잰다.
   여기서 영향이 작으면 이후 전부가 무의미해진다 — 가장 값싼 반증 기회다.
2. 측정 A로 C0의 붕괴를 재현한다(18건 중 8건 429). 기준선 확보.
3. C3(이미 구현됨)로 측정 A + B를 완주한다.
4. **F4만 따로, C1'에 대해 먼저 돌린다.** 판정 기준 ②가 여기서 갈린다.
   예상대로 통지 0건이면 **C1·C1'·C2를 한꺼번에 탈락**시키고 5·6단계를 생략한다
   (셋 다 "함수 코드가 보고한다"는 성질이 같다). 이게 가장 값싼 분기다.
5. C4(구현 비용 최소)를 붙여 측정 A + B. **"인프라 0개"의 실제 대가**를 확인한다.
6. **C6를 붙인다.** 푸시 후보 중 재시도 정책이 가장 강해 상한을 대표한다.
   C6가 C3를 못 이기면 C5는 볼 것도 없다(재시도가 더 약하다).
7. C5는 **C6가 C3를 이겼을 때만** 구현한다 — 그때는 "더 단순한 푸시"를 찾는 게 된다.
8. C2는 **4단계에서 C1'이 F4를 통과한 경우에만** 구현한다. VPC 작업 비용이 크다.

이 순서는 **가장 싼 반증부터** 놓았다. 4단계에서 푸시 계열 셋이 한꺼번에 떨어지고,
6단계에서 릴레이 푸시가 갈린다. 3~6단계에서 결론이 나면 7~8은 안 돌린다.
