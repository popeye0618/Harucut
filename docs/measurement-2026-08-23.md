# 측정 결과 — 2026-08-23

개선 전과 후를 같은 환경에서 실제로 돌려 잰 값이다.
그래프는 Grafana(http://localhost:3002)에, 원본 수치는 `monitoring/loadtest/results/*.json` 에 있다.

---

## 결론

**개선의 성과는 속도가 아니라 유실이다.**
개선 전 구조에서 처리를 빠르게 하려고 스레드를 2에서 20으로 늘리자
30건 중 **9건(30%)이 영구 손실**됐다. 개선 후에는 같은 조건에서 **30건 전부 성공**했다.

| | 개선 전 · 스레드 2 | 개선 전 · 스레드 20 | 개선 후 |
|---|---|---|---|
| 요청 | 30건 동시 | 30건 동시 | 30건 동시 |
| 최종 DONE | **30건** | 21건 | **30건** |
| 최종 FAILED | 0건 | **9건** | 0건 |
| **유실률** | **0%** | **30%** | **0%** |
| 전부 끝나기까지 | 30초 | **10초** | 53초 |
| 접수 응답 p95 | 1452ms | 1446ms | 1520ms |

**스레드를 늘리면 빨라지지만(30초 → 10초) 그만큼 잃는다(0% → 30%).**
개선 후는 다시 느려졌지만(53초) 하나도 잃지 않는다.
**처리량을 산 것이 아니라 손실을 없앤 것이다.**

---

## 실패 사유

개선 전 · 스레드 20 에서 실패한 9건의 사유는 전부 같다.

```
Rate Exceeded. (Service: Lambda, Status Code: 429, Request ID: 95e606f3-...)
```

동기 호출(`InvocationType.REQUEST_RESPONSE`)은 동시성 한도를 넘으면
**대기하지 않고 예외를 던진다.** 워커가 그 예외를 받아 Job 을 `FAILED` 로 확정하고,
재실행 배치는 `PENDING` 만 조회하므로 이 작업들은 아무도 다시 집지 않는다.

비동기 호출(`InvocationType.EVENT`)은 초과분이 Lambda 내부 큐에서 대기한다.
그래서 개선 후에는 같은 한도에서도 실패가 0이다.

## 측정 환경

| 항목 | 값 |
|---|---|
| 개선 전 코드 | `e32247a` — 동기 Lambda 호출 + `@Async` 스레드풀 |
| 개선 후 코드 | `main` (`c1b64dc`) — 비동기 호출 + SQS 결과 통지 |
| 앱 자원 | 컨테이너 CPU 2, 메모리 2GB (두 실행 동일) |
| DB · 캐시 | MySQL 8.0, Redis 7 (컨테이너) |
| Lambda | java21 · 2048MB · 타임아웃 60초 |
| **Lambda 동시 실행 한도** | **10 (계정 기본값)** |
| 프레임 | 컴포넌트 없는 최소 프레임, 캔버스 2000x6000 |
| 원본 사진 | 1000x1500 PNG 4장, 요청마다 새로 업로드 |

### 동시성 한도를 따로 조작하지 않았다

이 계정의 Lambda 동시 실행 한도가 **10** 이다(신규 계정 기본값. 일반적인 1000 이 아니다).
스레드 20으로 동시에 호출하면 10을 넘는 요청이 자연히 429 를 받는다.
예약 동시성을 걸어 인위적으로 낮출 필요가 없었고, 실제로 걸 수도 없다 —
AWS 가 미예약 동시성을 최소 10 남기도록 강제하기 때문이다.

### 이 측정으로는 확인되지 않는 것

**접수 응답 시간은 세 경우가 사실상 같다(1.4~1.5초).**
개선 전 코드(`e32247a`)도 이미 `@Async` 워커라 요청 스레드가 Lambda 를 기다리지 않았다.
7.9초를 붙잡고 있던 것은 요청 스레드가 아니라 **합성 워커 스레드**다.
개선 후에는 그 워커 스레드 자체가 사라졌다.

접수 p95 가 1.4초로 나온 것은 30건이 한꺼번에 도착한 첫 요청들이라
JIT 워밍업과 커넥션 확보가 겹친 값이다. 정상 부하에서의 값이 아니다.

**렌더 시간이 실제 서비스보다 짧다.**
측정용 프레임은 배경만 있고 컴포넌트가 없다. 실제 프레임(스티커·텍스트 다수)보다
Lambda 실행이 짧게 끝난다. 그래서 절대 시간은 운영값과 다르고,
**세 실행 사이의 비교만 유효하다.**

## 그래프 보는 법

http://localhost:3002 를 열면 대시보드가 바로 뜬다. 시간 범위는 최근 1시간이 기본이다.

세 실행이 시간순으로 이어져 있고, 범례에 실행 이름이 붙는다.

| 범례 | 실행 |
|---|---|
| `before-pool2` | 개선 전 · 스레드 2 |
| `before-pool20` | 개선 전 · 스레드 20 |
| `after` | 개선 후 |

### 바로 그 구간만 여는 링크

시간 범위가 URL 에 박혀 있어 클릭하면 해당 실행만 보인다.
대시보드 상단에도 같은 링크가 버튼으로 붙어 있다.

| 실행 | 구간 | 링크 |
|---|---|---|
| **전체 비교** | 03:23:28 ~ 03:28:16 | [세 실행 한 화면에](http://localhost:3002/d/harucut-compose?orgId=1&from=1787423008751&to=1787423296415) |
| 개선 전 · 스레드 2 | 03:23:58 ~ 03:24:28 | [열기](http://localhost:3002/d/harucut-compose?orgId=1&from=1787423008751&to=1787423098613) |
| 개선 전 · 스레드 20 | 03:25:35 ~ 03:25:46 | [열기](http://localhost:3002/d/harucut-compose?orgId=1&from=1787423105773&to=1787423176227) |
| 개선 후 | 03:26:53 ~ 03:27:46 | [열기](http://localhost:3002/d/harucut-compose?orgId=1&from=1787423183651&to=1787423296415) |

포트폴리오에 넣을 캡처 한 장은 **전체 비교**가 낫다.
세 구간이 나란히 보여서 설명 없이도 차이가 드러난다.

**유실 건수는 그래프에 없다.** 작업의 최종 상태라서 애플리케이션 메트릭이 아니다.
이 값은 위의 표와 `results/*.json`, 그리고 `compose_job` 테이블에 있다.

## 다시 돌리는 법

```bash
# 관측 스택 (한 번만)
docker compose -f monitoring/docker-compose.view.yml up -d

# 앱·DB 스택 + 계정·프레임 준비 (한 번만)
#   1) local 프로파일로 한 번 띄워 스키마 생성
#   2) 계정을 만든 뒤 플랜을 PRO 로 올린다 (BASIC 은 프레임 보관 한도가 0)
#   3) 그 계정으로 프레임 생성
node monitoring/loadtest/run.mjs seed --email <계정>

# 시나리오 실행
powershell -File monitoring/loadtest/run-scenario.ps1 -Label before-pool2  -Image harucut:before -Pool 2  -N 30
powershell -File monitoring/loadtest/run-scenario.ps1 -Label before-pool20 -Image harucut:before -Pool 20 -N 30
powershell -File monitoring/loadtest/run-scenario.ps1 -Label after         -Image harucut:after  -Pool 2  -N 30
```

이미지는 이렇게 만들었다.

```bash
docker build -t harucut:after .                  # main
git worktree add /tmp/before e32247a
cd /tmp/before && docker build -t harucut:before .
```

### 주의: 원본 사진은 요청마다 새로 올려야 한다

합성에 성공하면 서버가 원본 4장을 S3 에서 지운다(결과만 보관하는 정책).
같은 key 를 여러 요청이 공유하면 첫 성공 이후 나머지가 전부
`The specified key does not exist` 404 로 죽는다.
`run.mjs` 는 실행마다 `요청 수 x 4` 장을 새로 업로드한다.
